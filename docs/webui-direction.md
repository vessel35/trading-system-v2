# WebUI 개발 방향·개념 결정

이 문서는 이 저장소에 붙일 WebUI(웹 사용자 인터페이스)의 개발 방향과 개념을 기록한다. 저장소 전략과
프레임워크·API 방식은 발주자가 확정했고, 그 결정을 뒷받침하는 근거와 남은 세부 결정을 함께 남긴다.

## 전제

WebUI는 종합 내부 콘솔이다. 백테스트 결과와 Evidence(실행별 상세 근거)를 조회·분석하고, 전략과
백테스트 실행을 관리하며, 실거래를 모니터링·제어하고, 지표와 리서치를 시각화한다. 개발은 사람이 AI
에이전트를 지휘해 진행하는 방식(이하 "바이브코딩")으로 하고, 배포는 내부·개인용 자가 호스팅으로
소수 사용자를 대상으로 한다.

## 확정 결정

### 결정 1 — 저장소는 모노레포

WebUI의 API 서비스를 `services/web-api`(Python 형제 패키지)로, 웹 앱을 최상위 `apps/web`으로 이
저장소 트리 안에 둔다. 바이브코딩에서 저장소 경계의 실질 효과는 AI 에이전트가 한 번에 볼 수 있는
컨텍스트의 범위와, 하나의 논리적 변경이 몇 개의 저장소·리뷰로 쪼개지는가이다. WebUI가 화면에 올리는
계약은 `core_lib`의 값 타입·지표 정의에서 시작해 카탈로그(`backtest_db`)와 Evidence 스키마를 거쳐 API
응답 모델을 지나 프런트엔드 타입까지 이어지는 하나의 사슬이며, 이 사슬 전체가 한 트리에 있으면
"지표에 필드 하나 추가"가 한 커밋·한 리뷰로 끝난다. 또한 API 서비스는 반드시 Python이며 `core_lib`을
import해야 하므로(결정 2), 기존 `backtest-service`가 그러하듯 `core_lib`을 editable로 링크하는 또
하나의 `services/*` 형제 패키지가 되는 것이 가장 자연스럽다. 멀티레포의 유일한 실질 논거인 폴리글랏
도구 비용은 프런트엔드를 자체 `package.json`과 `node_modules`를 가진 하위 디렉터리로 격리하면 충분히
억제된다. 이 결정은 네 서비스(signal·wallet·backtest·collector)를 한 모노레포에 두되 서비스별로
독립 배포한다는 기존 결정과도 일치한다.

### 결정 2 — API 계층은 Python FastAPI backend-for-frontend가 `core_lib`을 재사용

현재 이 저장소에는 HTTP API가 없다. 백테스트는 `services/backtest-service/backtest_service/runner.py`의
`run_backtest`를 프로그램으로 직접 호출해 실행한다. WebUI를 붙이려면 API 계층이 필요한데, 이를 Python
FastAPI backend-for-frontend로 두고 `core_lib`을 직접 import해 재사용한다.

풀스택 JavaScript(예를 들어 Next.js가 데이터베이스에 직접 붙어 로직을 TypeScript로 다시 유도하는
방식)를 배제하는 이유는 단일 표준 구현 불변식이다. 상세 설계서의 "위반 불가" 블록 첫 항목은 전략·지표·
사이징·비용계산을 복제 없이 하나의 공유 라이브러리에 두고 백테스트·페이퍼·라이브가 함께 import한다고
규정한다. 지표·회계·판정 로직을 TypeScript로 다시 만드는 순간 이 불변식을 위반한다. 특히 `core_lib`의
파산확률 추정은 고정 시드 부트스트랩(`random.Random(seed)`, 반복 10,000회)이고, `config_hash`는 스물세
개 필드를 정해진 순서로 SHA-256 해싱하며, Evidence의 금액은 부동소수점이 아니라 10의 8제곱으로 스케일된
정수로 저장된다. 이 계산들을 다른 언어로 동일하게 재현하는 것은 사실상 불가능하고, 재현이 어긋나면
저장된 진실과 화면의 수치가 갈린다. 또한 JavaScript 프런트엔드가 데이터베이스에 직접 붙으면 스키마가
공들여 세운 읽기 전용 역할 분리를 우회한다.

따라서 FastAPI 서비스가 `backtest-service`와 똑같이 `core_lib`을 editable로 링크해 지표·회계·판정
로직과 `RunConfig`·`config_hash`를 그 하나의 구현에서 가져오고, 카탈로그(읽기 전용 역할)와 Evidence를
읽어 타입 있는 REST/JSON으로 노출하며, 라이브 모니터링에는 Server-Sent Events 스트림을 얹는다. 백테스트
트리거는 기존 `run_backtest`를 재사용하므로 실행 로직도 복제하지 않는다. 타입 계약은 FastAPI가 pydantic
응답 모델에서 OpenAPI 문서를 자동으로 내고, 그 문서에서 TypeScript 클라이언트를 생성해(예를 들어
`openapi-typescript`나 `orval`) 프런트엔드가 손으로 쓴 타입이 아니라 생성된 타입만 소비하게 흐른다.
그 결과 서버는 pydantic 응답 모델, 클라이언트는 생성된 TypeScript 타입으로 양쪽이 같은 계약에 묶여
바이브코딩에서 형태를 틀릴 여지가 줄어든다. 한 가지 규약을 못박아 둔다. Decimal 금액은 JSON에서
문자열로 직렬화한다. 프런트엔드는 표시만 하고 금액 산술을 하지 않으므로 정확성을 문자열로 보존한다.

### 결정 3 — 프런트엔드는 React·Vite·TypeScript 단일 페이지 앱

Python API가 모든 로직을 소유하므로 프런트엔드는 순수 표현 계층으로 두는 것이 경계가 가장 선명하다.
React와 Vite 기반의 TypeScript(strict) 단일 페이지 앱으로 한다. Next.js는 학습 데이터가 가장 두껍다는
장점이 있으나 서버 컴포넌트와 서버 액션이 로직을 Next 서버로 새게 만들 유혹이 "로직은 Python 하나에만"이라는
원칙과 충돌하므로 대안으로만 남긴다. 컴포넌트와 스타일링은 shadcn/ui(Radix 기반)와 Tailwind CSS로 하고,
배터리 포함형을 선호하면 Mantine이 대안이다. 차트는 데이터 성격에 따라 나눈다. 캔들·OHLC·매매 마커와
자본곡선 같은 금융 시계열에는 TradingView Lightweight Charts를, 실행 간 지표 비교·R-multiple 분포·
드로다운 곡선 같은 일반 차트에는 Recharts를 쓴다. 실행 비교 그리드와 지표 표는 TanStack Table로, 서버
상태와 데이터 페칭은 TanStack Query로, 실시간 모니터링은 Server-Sent Events를 우선하고 진짜 양방향이
필요할 때만 websocket을 검토한다.

## 안전 도메인 분리

읽기 중심의 연구·백테스트 세계는 데이터 원천에서 `core_lib`을 거쳐 UI라는 읽기 종착점에 이르는 방향성
비순환 구조이고, 백테스트 트리거는 카탈로그와 Evidence에 덧붙이는 전방향 동작일 뿐 데이터·피처·신호로
되돌아가지 않는다. 따라서 읽기 연구 화면은 데이터 누수나 은닉 상태의 위험을 새로 만들지 않는다. 진짜
순환은 사람이 낀 라이브 제어 루프 하나뿐이다. 사람이 화면에서 명령을 내면 제어 서비스가 거래소에 주문을
내고, 체결이 지갑 상태를 바꾸고, 그 상태가 모니터링으로 다시 사람에게 보여져 다음 명령을 낳는다. 이
루프는 없앨 수 없으므로, 설계의 임무는 이 루프의 쓰기 경로를 강하게 게이트하고 바이브코딩으로 만든
연구 화면이 이 루프로 들어가는 경로를 아예 갖지 못하게 하는 것이다.

구체적으로, 라이브 주문과 지갑 쓰기가 가능한 코드는 별도 프로세스·별도 배포·별도 자격증명의 hardened
서비스(`services/live-control`)로 격리한다. 연구 API는 이 서비스의 주문 코드를 import하거나 호출할 수
없고, 거래소 키와 지갑 데이터베이스 쓰기 자격증명은 오직 이 서비스만 보유한다. 라이브에 대해서도 기본은
읽기 전용이며, 모니터링(포지션·미체결 주문·잔고·라이브 손익)은 지갑 데이터베이스의 읽기 전용 역할로
서비스하고 제어보다 훨씬 먼저 출시한다. 제어 경로는 심층 방어로 게이트한다. 내부용이라도 실주문을 내는
엔드포인트에는 최소한의 실제 인증이 필요하고, 제어 동작은 주문 내용을 되비추는 확인과 서버측 idempotency
키를 요구하며, 제어 서비스는 UI와 독립적으로 자체 가드레일(최대 주문 크기, 심볼 허용 목록, 요청 속도
제한, kill switch)과 append-only 감사 로그를 강제한다. UI는 신뢰되지 않는 쪽이고 신뢰 경계는 제어
서비스다. 거래소로의 원시 통과 경로는 존재하지 않는다.

## 단계별 로드맵

가장 빨리 쓸모를 내는 순서로, 위험을 뒤로 미룬다.

1. **기반.** FastAPI 연구 API와 Vite·React 앱의 골격, OpenAPI에서 TypeScript 클라이언트 생성, 카탈로그
   브라우즈(실행 목록·요약 지표·필터). 가장 빠른 쓸모는 브라우저에서 실행과 지표를 보는 것이다.
2. **Evidence 분석.** 실행별 상세(거래·체결·자본곡선·드로다운·무결성 검사·funding)와 실행 간 지표
   비교. 개선을 주 목적으로 삼는 이 시스템의 핵심 가치인 연구 콘솔이다.
3. **실행 관리.** 폼으로 `RunConfig`를 구성하고(서버측 pydantic 모델이 검증), 백테스트를 트리거하고,
   상태를 폴링·스트림으로 보고, 사전등록과 파라미터 스윕을 붙인다. 전부 dry-run이며 라이브는 읽기 전용.
4. **라이브 모니터링(읽기 전용).** 라이브 시스템의 상태를 지갑 데이터베이스 읽기 전용 역할로 본다.
   제어는 없고, 라이브 금융 데이터 읽기에도 인증을 강제한다.
5. **라이브 제어.** 별도 hardened 서비스와 게이트된 UI 동작으로, 인증·확인·가드레일·감사·kill switch
   뒤에 둔다. 가장 마지막에 만들고, 앞 단계들과 같은 느슨한 바이브코딩 표준으로 만들지 않는다.

## 제안 디렉터리 레이아웃

```
services/core-lib/          # 변경 없음 · 단일 표준 (core_lib)
services/backtest-service/  # 변경 없음 · Engine, run_backtest
services/web-api/           # 신규 · FastAPI 연구/카탈로그 backend-for-frontend
                            #   core_lib editable 링크, runner.run_backtest 재사용
services/live-control/      # 신규 · 분리 hardened · 주문 발주·지갑 쓰기 유일 코드 (5단계)
apps/web/                   # 신규 · React + Vite + TypeScript 단일 페이지 앱 (자체 package.json)
init-scripts/               # web-api용 읽기 전용 역할 추가 가능
docs/fullspec/              # 변경 없음
```

`web-api`는 `services/requirements-dev.txt`에 editable 경로 하나를 더한 또 하나의 `services/*`
패키지이며 로직을 복제하지 않는다. `apps/web`은 자체 Node 도구를 가지며 Python 패키징과 서로
간섭하지 않는다. 한 저장소, 두 도구 체인, 깨끗한 하위 디렉터리 경계다.

## 남은 결정 (구현 단계 또는 발주자 확정)

첫째, 라이브 제어 서비스를 모노레포 안 형제로 두되 배포·자격증명·리뷰로 격리할지, 아니면 물리적 최대
격리를 위해 별도 저장소로 완전히 뗄지. 위험 선호의 문제다.

둘째, 라이브 단계(4·5단계)는 현재의 백테스트 전용·데이터베이스 읽기 전용·dry-run 프리셋 밖의 능력을
요구한다. 라이브 모니터링(읽기)조차 지갑 데이터베이스 접근을 요구하므로, 별도 하네스 프리셋과 그에 따른
자격증명·역할 결정이 선행되어야 착수할 수 있다.

셋째, 인증의 강도. 내부·개인용이라 무거운 인증은 불필요하지만 제어 엔드포인트에는 최소한의 실제 인증이
필수다. 단일 사용자 토큰 수준으로 갈지, 제어 동작에 한해 2차 확인을 더할지.

넷째, 컴포넌트 라이브러리를 shadcn/ui로 갈지 Mantine으로 갈지, 차트를 Lightweight Charts와 Recharts
조합으로 확정할지. 기능상 어느 쪽이든 되므로 취향과 친숙도로 정한다.

다섯째, `web-api`가 Evidence SQLite 파일 경로에 어떻게 접근할지. `backtest_run.evidence_path`가 파일
경로를 담으므로, 조회 서비스가 그 파일에 물리적으로 닿는 배치(실행 호스트와 같은 호스트인지, 공유
볼륨인지)를 확정해야 한다.
