# 배포 정책 결함 다섯의 수정 설계

이 문서는 커밋 `a525c5a` 시점의 배포 정책 경로에 남은 결함 가운데 다섯을 무엇으로
판단했고 무엇을 만족해야 닫힌 것으로 보는지를 정한다. 구현 방법은 정하지 않는다.
지켜야 할 규칙의 본문은 `docs/strategy-authoring-contract.md`의 5.1 절과 6.1 절과
6.5 절과 7 절에 있으며, 이 문서는 그 규칙을 어느 결함에 걸어야 하는지를 잇는다.

## 1. 배경

전략과 자금 관리 정책을 **파일로 두는 것만으로** 배포할 수 있게 만드는 작업이 세 차례
독립 리뷰를 거쳤다. 매 차례 Blocking이 나왔고, 그중 상당수는 **앞 차례의 고침이 만든
것**이었다. 형 검사기에 보이는 union을 넓히려다 정상 접근을 막았고, 다시 좁히려다
배포 mode 이름과의 비교를 막았다. 화면도 한 경로만 고치고 다른 경로를 빠뜨리는 일이
반복되었다.

그래서 이 설계는 **결함마다 그것이 걸려 있는 경로를 모두 세는 것**을 요구한다. 고침
하나가 닫는 경로와 새로 막는 경로를 함께 적지 않으면 같은 일이 또 일어난다.

이 설계 자체도 한 차례 독립 검토를 받았고, 그 검토가 낸 Blocking 아홉을 반영해 다시
썼다. 2.3의 판단은 그 검토에서 기각되어 뒤집혔고, 2.5는 정상 경로 둘을 함께 막는
것으로 드러나 조건을 좁혔으며, 닫힘 조건 대부분이 시험으로 옮길 만큼 정밀하지 않아
관찰값을 명시했다.

## 2. 범위

이번 변경은 아래 다섯을 닫는다. 화면이 **고를 정책이 하나도 없을 때 실행을 막는 것은
이번 범위가 아니다.** 실제 Web API는 `vessel-reference` 하나만 코드 metadata로 보강하고
그 밖의 등록 전략에는 빈 목록을 내리므로, 지금 그 차단을 넣으면 배포된 전략이 모두
화면에서 막힌다. Web API를 공통 전략 registry에 잇는 일이 선행되어야 하며 그것은
`strategy_loading_and_placement_design.md`가 이미 미완료로 적어 둔 작업이다. 그 작업이
끝난 뒤에 화면 차단을 다룬다.

같은 이유로 화면이 전략 조회 중이거나 실패했을 때 `manual`을 채워 넣는 현재 동작도
이번에는 건드리지 않는다.

## 3. 이번 변경에 드는 다섯

### 3.1 최종 union으로 세워 보지 않는다

설정 모델을 만든 뒤 **기본 제공 하나와만** 묶어 시험한다. 그래서 서로에 대해서만
어긋나는 정책 둘이 각자 통과한 뒤 실제 union에서 부딪힌다. 리뷰는 두 배포 정책의
설정이 같은 스키마 이름을 쓰게 만들어, 둘 다 통과한 뒤 최종 OpenAPI가 문자열 갈래를
정수로 잘못 표기하게 했다.

**닫힌 것으로 보는 조건.** 정책 하나를 받아들일지 판단할 때, 기본 제공 둘과 앞서
받아들인 전부와 이 정책이 든 union을 만들고 **그 자리에서 JSON 스키마를 뽑는다.** 그
스키마에서 다음이 모두 성립해야 받아들인다.

- 모든 mode의 discriminator 대응이 **그 mode 자신의 갈래**를 가리킨다.
- 앞서 받아들인 갈래들의 대응과 필드 type이 **하나도 변하지 않는다.**
- 이름이 겹치지 않는다. 견주는 이름의 범위는 **갈래 자체의 이름과, 그 갈래가 재귀적으로
  참조하는 모든 스키마 구성요소의 이름**이며 기본 제공 둘의 것까지 포함한다.

**시험은 두 가지 충돌을 각각 둔다.** 하나는 생성된 갈래의 이름이 겹치는 경우이고,
다른 하나는 서로 다른 중첩 설정 형이 같은 스키마 이름을 쓰는 경우다. 각각에서 그
정책만 빠지고 나머지는 그대로 받아들여지는지 확인한다.

### 3.2 목록과 기본값이 어긋난다

고를 수 있는 mode 목록만 거르고 기본값은 따로 만들어, 목록에 없는 mode를 기본값이
가리킨다. 화면은 기본값에서 시작하므로 **거부되는 mode를 제출한다.**

**닫힌 것으로 보는 조건.** 목록과 기본값을 한 곳에서 함께 만들고 아래 세 규칙을 둔다.

- 남는 mode가 하나도 없으면 목록도 기본값도 비운다.
- 전략이 밝힌 기본값만 빠지고 다른 mode가 남으면 **목록은 그대로 내고 기본값만 비운다.**
  남은 것 중 첫째를 골라 주면 전략이 선언한 기본값을 시스템이 바꾼 것이 된다.
- 그 밖의 경우 기본값의 mode는 반드시 목록 안에 있다.

**기본값은 정책이 돌려준 값을 그대로 내보내지 않는다.** 정책이 요청한 것과 다른 mode를
담거나 스키마 밖 필드를 담을 수 있으므로, 3.1에서 만든 최종 union으로 검증해 통과한
것만 내보낸다. 통과하지 못하면 기본값을 비운다.

**불변식 하나로 시험한다.** 응답의 기본값은 비어 있거나, 그 `mode`가 목록 안에 있고
최종 union이 그 값을 받아들인다. 시험은 기본값만 탈락한 경우와 전부 탈락한 경우와
정책이 엉뚱한 값을 돌려주는 경우를 각각 둔다.

### 3.3 형 검사기 자리의 discriminator

배포 정책을 대신하는 자리의 `mode`를 좁은 자리표시로 두어, 배포된 mode의 이름과 견주는
코드가 형 검사에서 막힌다. 앞서 `str`로 두었을 때는 반대로 기본 제공 정책의 설정을
읽지 못했다.

**닫힌 것으로 보는 조건.** 그 자리의 `mode`는 어떤 이름도 될 수 있게 두고, 기본 제공
정책의 설정은 **`mode` 값이 아니라 형으로 갈라** 읽는다. 형 검사를 실제로 돌려 셋을
각각 확인한다.

- 배포된 mode의 이름과 견주는 코드가 **통과한다.**
- 기본 제공 형에 속하는지 확인한 뒤 그 설정을 읽는 코드가 **통과한다.**
- 아무 확인 없이 기본 제공 정책의 설정을 읽는 코드가 **거부된다.**

### 3.4 전략 목록을 다시 받는 것이 화면을 되돌린다

전략을 맞추는 처리가 목록을 다시 받을 때마다 돌아, 고른 mode와 적어 둔 설정을 전략
기본값으로 되돌린다. 전략을 바꾼 것과 목록을 다시 받은 것을 구분하지 않는다.

**닫힌 것으로 보는 조건.** 네 가지 상태 변화를 각각 정하고 각각 시험한다.

- 같은 전략을 같은 내용으로 다시 받으면 **사용자가 고르고 적은 값을 보존한다.**
- 사용자가 전략을 A에서 B로 바꾸면 **B가 밝힌 기본값으로 맞춘다.**
- 실패한 실행 설정을 폼으로 불러오면 **불러온 값을 보존한다.** 전략을 맞추는 처리가
  그 직후에 기본값으로 덮지 않는다.
- 같은 전략을 다시 받았는데 지금 고른 값이 새 내용에서 더는 유효하지 않으면 **그
  사실을 말한다.** 조용히 보존하는 것과 조용히 되돌리는 것은 둘 다 틀렸다.

A에서 B로 갔다가 A로 돌아왔을 때 앞서 A에서 적어 둔 설정은 **보존한다.** 배포 정책의
설정은 mode마다 따로 남으므로 그것을 지울 이유가 없다.

### 3.5 축이 없는데 축을 쓰는 스윕이 켜진다

배포 mode에서는 축 후보를 비웠지만 스윕 자체를 막지 않아, 앞 정책의 축 입력이 그대로
남아 **없는 파라미터를 제출한다.**

**닫힌 것으로 보는 조건.** 막는 것은 **축을 쓰는 스윕 종류에 한한다.** 서버 계약에서
축을 받는 것은 grid뿐이고 walk-forward는 fold만, IS/OOS는 split만 받는다. 축 후보가
없다고 그 둘까지 막으면 **파라미터가 없는 전략을 검증할 방법이 사라진다.**

- 축 후보가 없으면 grid 제출을 막는다.
- 같은 상태에서 walk-forward와 IS/OOS는 그대로 제출된다. 이것을 시험으로 둔다.
- 요약과 선택과 제출과 버튼 이름이 같은 근거를 본다.

**축 후보가 없을 때 지금은 자유 입력 축을 일부러 보여 준다.** 그 경로를 없앨지, 앞
정책의 후보만 비우고 사용자가 축을 직접 적게 남길지를 구현 전에 정한다. 이 설계는
**남기는 쪽**을 택한다 — 전략 파라미터가 없어도 자금 관리 설정을 축으로 쓰고 싶을 수
있고, 그것을 막을 근거가 없다. 다만 앞 정책의 이름이 남아 있으면 안 된다.

## 4. 별도 변경으로 미루는 둘

**요청마다 정책을 생성하는 것.** 전략 목록을 만들 때 정책의 기본값을 얻으려고 요청마다
정책을 생성한다. 예외를 가두는 것으로는 멈추는 정책을 막지 못한다. **기동 시점에 한 번
만들어 두는 것으로도 멈춤은 사라지지 않는다** — 요청 대신 기동이 멈출 뿐이다. 실제로
막으려면 정책의 코드를 별도 프로세스에서 시간 제한과 함께 돌리거나, 배포 정책의 코드를
아예 부르지 않고 선언만으로 기본값을 얻어야 한다. 어느 쪽인지는 이 설계가 정하지
않는다.

**Web API를 공통 전략 registry에 잇는 것.** 2 장에 적은 이유로 화면 차단이 여기에
걸려 있다.

두 가지 모두 이 설계가 해결했다고 말하지 않는다.

## 5. 무엇을 만족하면 닫힌 것인가

- 결함마다 **되돌리면 실패하는 시험**이 있다. 고침을 지우고 시험이 그대로 통과하면
  그 시험은 결함을 물지 않는 것이다.
- 고침이 **새로 막는 것**을 항목마다 적는다. 세 차례 리뷰에서 반복된 실패가 이것을
  적지 않은 데서 나왔다.
- 저장소 루트에서 `.venv/bin/python -m pytest services -q`가 통과하고, 여덟 서비스
  각각에서 `ruff check`와 `ruff format --check`와 `mypy`가 통과하며, `apps/web`에서
  `npm test`와 `npm run typecheck`가 통과한다.
- 생성된 API 타입을 다시 뽑아도 의도한 것 밖의 변화가 없다.

## 6. 하지 않는 것

- 전략의 진입과 청산 판단, 자금 관리 수식, 주문 실행 방식은 건드리지 않는다.
- 기본 제공 두 정책의 설정 모델은 손으로 쓴 그대로 두어 이미 나간 스키마와 오류
  문구가 움직이지 않게 한다.
- 화면이 고를 정책을 하나도 받지 못했을 때의 처리는 2 장에 적은 대로 다루지 않는다.
- 데이터베이스는 읽기만 한다. 비밀은 파일에 쓰지 않는다.
