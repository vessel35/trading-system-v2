# 전략 개발 Agent와 실행 능력 목록 설계

이 문서는 전략 기술 문서를 실행 가능한 전략으로 옮기는 Agent 워크플로의 최종 설계이며, 실행 능력 목록과 작성 Agent와 독립 검증 Agent는 아직 구현되지 않았다.

## 1. 목표와 완료 상태

이 단계의 산출물은 특정 전략이 아니라 반복해서 신규 전략을 개발할 수 있는 Agent 워크플로다.
입력은 사람이 쓴 전략 기술 문서이고, 출력은 문서의 규칙대로 백테스트가 오류 없이 실행되며
화면에서 실행 상태와 결과를 조회할 수 있는 전략이다.

코드 작성이나 카탈로그 등록만으로 완료로 보지 않는다. 전략 구현, 등록, 실행과 계산 검증이
모두 끝나야 한다.

현재 신규 전략이 따라야 할 계약은 `DecisionIntent`와 `MoneyManagementPolicy`의 목표 계약이다.
기존 Engine과 `StrategyAdapter`가 legacy `TradingSignal`을 수용하는 것은 호환 경계이며, Agent가
신규 전략에 legacy 보호가격과 leverage 필드를 추가할 근거가 아니다.

## 2. 실행 능력 목록이 필요한 이유

Agent가 전략 기술 문서를 구현할 수 있는지 판정하려면 두 종류의 사실이 필요하다. 지표와 패턴
같은 계산 재료는 현재 레지스트리에서 조회할 수 있다. 반면 실행당 timeframe과 종목 수, 지원
청산 방식과 보호가격 표현처럼 플랫폼이 할 수 있는 일은 코드 여러 곳에 흩어져 있다.

Agent가 매번 코드를 탐색해 능력을 추측하면 같은 문서에도 다른 판정을 내리거나 없는 기능을
지원한다고 오해할 수 있다. 그래서 실행 능력을 기계가 조회하고 검사가 대조할 수 있는 목록으로
고정한다.

## 3. 실행 능력 목록의 형태

실행 능력 목록은 `services/core-lib/core_lib/capabilities.py`에 둔다. Agent가 읽을 수 있고
저장소 검사가 실제 코드와 대조할 수 있어야 하므로 서술 문서만으로 두지 않는다.

목록에는 최소한 다음 사실을 담는다.

1. 실행당 전략 timeframe 수와 자금관리 정책이 요구할 수 있는 timeframe 종류를 담는다.
2. 실행당 종목 수를 담는다.
3. 거래소 실제 캔들과 파생 캔들의 지원 여부를 담는다.
4. 보호가격을 어느 계층이 만들고 어떤 방식으로 표현할 수 있는지를 담는다.
5. 전량 청산, 부분 익절과 트레일링의 지원 여부를 담는다.
6. 거래당 위험과 일일 및 주간 한도, 연패 중단 같은 거래 간 리스크 규칙의 지원 여부를 담는다.
7. 지표와 패턴 선언 방법, 공통 `series_key()` 소비 방식과 결과 저장 방식을 담는다.

지원하지 않는 기능도 명시한다. Agent가 전략 문서의 요구를 판정하려면 있는 기능만큼 없는
기능이 중요하다.

## 4. 능력 목록의 드리프트 방지

목록의 항목은 가능한 한 정확한 집합 단언으로 코드와 대조한다. 다음과 같은 검사가 그 예다.

1. 등록된 자금관리 모드가 정확히 `manual`과 `turtle`인지 확인한다.
2. 정책 요구 timeframe이 strategy timeframe과 `1d`인지 확인한다.
3. `RunConfig`가 전략 timeframe과 종목을 각각 하나만 받는지 확인한다.
4. `DecisionIntent` 필드에 손절, 익절, 수량과 leverage가 없는지 확인한다.
5. 실행 matcher가 부분 익절이나 트레일링을 실제 지원하지 않는 상태인지 확인한다.

플랫폼 기능이 추가되면 이 검사가 먼저 깨져 능력 목록을 함께 갱신하게 해야 한다. 검사로 못
박을 수 없는 주장은 능력 목록에 넣지 않고, 별도 조사 대상임을 명시한다. 조용히 낡을 수 있는
서술을 기계 판정 근거로 사용하지 않는다.

## 5. 전체 워크플로와 역할 분리

한 Agent가 요구사항 확정, 구현, 검증과 채택을 모두 맡지 않는다. 메인 세션이 사용자 대화와
단계 전환을 조정하고, `strategy-author`가 구현과 등록을 맡으며, `strategy-verifier`가 계산을
독립적으로 검증한다.

검증 주체를 분리하는 이유는 구현자가 가진 같은 해석 오류가 자기 검증을 그대로 통과하는 것을
막기 위해서다. verifier는 읽기 전용으로 결과를 보고하고, 수정이 필요하면 author 단계로
돌려보낸다.

## 6. `strategy-author`의 책임

`strategy-author`의 입력은 사람이 작성한 전략 기술 문서다. 출력은 등록되어 백테스트가
실행되는 전략이거나, 진행할 수 없는 이유와 필요한 다음 입력을 구조화한 보고다.

### 6.1 요구사항 구조화

Agent는 방향 판단, 진입 조건, 청산 규칙, 리스크 규칙, timeframe, 종목 범위와 사용하는 지표
및 패턴을 문서에서 구조화한다. 문서가 비워 둔 값이나 서로 모순되는 요구를 먼저 찾는다.

### 6.2 재료와 능력 대조

지표와 패턴은 각각의 레지스트리에서 조회하고, 실행 능력은 능력 목록에서 조회한다. 지표나
패턴을 전략 안에 다시 구현하거나 실행 코드를 뒤져 지원 여부를 추측하지 않는다.

### 6.3 막힘의 분류

막힘은 다음 세 종류로 구분한다.

| 종류 | 판정 기준 | 처리 방식 |
|---|---|---|
| 문서가 비워 둔 값 | 파라미터나 규칙이 `TODO`로 남았거나 문서에 없다. | Agent는 값을 지어내지 않고 사용자에게 물을 질문을 구조화한다. |
| 계산 재료의 부재 | 필요한 지표, 패턴이나 캔들 종류가 레지스트리에 없다. | Agent는 먼저 구현해야 할 재료를 목록으로 보고하고 종료한다. |
| 실행 능력의 부재 | 멀티 timeframe, 부분 익절처럼 현재 실행 구조가 요구를 표현할 수 없다. | Agent는 지원하지 않는 능력과 가능한 범위를 보고하고 우회 구현 없이 종료한다. |

전체가 막혀도 가능한 부분이 있으면 함께 밝힌다. 전략 문서가 실험 순서를 정했다면 현재 능력으로
어느 단계까지 가능한지 보고한다.

사용자 답이 필요할 때 Agent는 대화 중인 상태로 남아 있지 않는다. 이미 확정한 사실, 미완료
산출물, 필요한 입력과 질문 목록을 구조화하고 종료한다. 메인 세션이 사용자 답을 받은 뒤 그
답과 이전 상태를 다음 배정에 함께 넘긴다.

### 6.4 구현과 등록

막힘이 없으면 canonical contract와 `develop-trading-strategies` skill을 따라 구현한다. 전략은
진입과 청산 edge만 소유하고, 자금관리와 실행 책임을 끌어오지 않는다.

Agent는 전략 코드, 메타데이터, 대표 설정, 허용 목록, 판이 매겨진 멱등 등록 SQL과 필요한
테스트를 같은 전략 changeset에 포함한다. 등록 직후에는 읽기 전용 사전 점검으로 코드와
카탈로그가 맞는지 확인한다.

Agent는 기존 Evidence 저장 경로와 Engine 조립을 사용한다. 자기 편의를 위한 저장 방식이나
실행 경로를 새로 만들지 않는다.

### 6.5 화면 완료 조건

전략은 화면에서 선택해 실행할 수 있고 상태와 결과를 조회할 수 있어야 한다. 코드에서만
실행되는 전략은 완료가 아니다.

파라미터 때문에 화면 수정이 필요하면 전략 내부에 값을 고정할지 화면을 확장할지를 사용자에게
묻는다. 화면 수정 자체는 `strategy-author`의 책임이 아니며, 사용자가 화면 변경을 선택하면
별도 UI 작업으로 요청한다.

## 7. `strategy-verifier`의 책임

`strategy-verifier`는 구현 산출물을 읽고 계산이 문서와 플랫폼 계약에 맞는지 독립적으로
검증한다. 구현 파일을 수정하지 않는다.

verifier는 다음 계산을 확인한다.

1. 전략이 소비한 지표와 패턴 값을 독립 기준과 대조한다.
2. 대표 진입과 청산 판단을 손 계산으로 대조한다.
3. Evidence에서 거래를 되짚어 손익, 수수료, 슬리피지, 펀딩과 보호가격 계산을 검산한다.
4. 시점, look-ahead, next-bar 체결과 결정성 증거를 확인한다.
5. 선언, 등록, 정책 capability와 실제 실행 결과가 맞는지 확인한다.

검증이 통과하지 않으면 성적이 좋아도 전략을 채택하지 않는다. verifier가 발견한 불일치는
author에게 수정 과제로 돌리고, 수정 뒤 독립 검증을 다시 수행한다.

## 8. 인수 시험

`docs/samples_for_strategy_agent/`의 두 전략 문서를 인수 시험으로 고정한다. 두 문서는
`0dd26a2`에 저장되어 있지만 현재 `feat/strategy-authoring-change`에는 포함되지 않았으므로,
Agent 워크플로를 구현하기 전에 같은 원본을 현재 이력에 통합해야 한다.

`00.EMA_StochasticRSI.md`는 계산 재료의 부재로 막혀야 한다. EMA 200, Stochastic RSI와
마루보즈는 있지만 하이킨아시 캔들이 없다. 올바른 결과는 하이킨아시를 먼저 구현해야 한다고
보고하는 것이다.

`00.TCT_MultiTF.md`는 실행 능력의 부재로 막혀야 한다. 멀티 timeframe, 구조 기반 손절, 부분
익절, 트레일링, 거래 간 리스크 상태와 다종목을 현재 실행 구조가 지원하지 않는다. 올바른 결과는
막힌 능력을 열거하고, 문서가 정한 첫 실험 단계인 H1 범위는 가능하다고 함께 보고하는 것이다.

두 문서는 서로 다른 이유로 막히므로 Agent가 문서의 빈값, 계산 재료와 실행 능력을 구분하는지
확인할 수 있다.

## 9. 범위 밖

- 이 설계 작업에서 하이킨아시, 멀티 timeframe, 구조 기반 손절, 부분 익절, 트레일링과 거래 간
  리스크 기능을 구현하지 않는다.
- 이 설계 작업에서 신규 전략을 만들지 않는다.
- Agent가 지표나 패턴을 전략 안에 재구현하지 않는다.
- Agent가 화면 변경을 사용자 승인 없이 수행하지 않는다.
- verifier는 구현 파일을 고치지 않는다.

## 10. 완료 기준

- 실행 능력 목록이 코드에서 조회 가능해야 하고 실제 구현과 어긋나면 검사가 실패해야 한다.
- `strategy-author`와 `strategy-verifier` 정의가 있고 각 역할의 lane과 사용 도구가 명시되어야
  한다.
- author가 문서 빈값, 계산 재료 부재와 실행 능력 부재를 서로 다르게 처리해야 한다.
- author가 구현된 지표와 패턴을 레지스트리에서 사용하고 전략 안에 다시 구현하지 않아야 한다.
- author가 전략 구현과 허용 목록과 등록 SQL을 함께 만들고 사전 점검을 통과해야 한다.
- 사용자 입력이 필요할 때 구조화된 종료 보고와 재배정 규약이 작동해야 한다.
- 화면에서 실행과 상태 및 결과 조회가 가능해야 전략을 완료로 판정해야 한다.
- verifier가 계산과 Evidence를 독립적으로 대조하고 실패한 전략의 채택을 막아야 한다.
- 두 인수 시험 문서에 대한 판정이 사람이 확인한 재료 및 능력 판정과 같아야 한다.
- 관련 pytest, mypy와 ruff가 통과하고 건너뛴 검사 수를 함께 보고해야 한다.

## 11. 검토에서 바로잡힌 사실

- 현재 `RunConfig`는 실행당 전략 timeframe 하나와 symbol 하나를 받는다. 멀티 timeframe 전략과
  다종목 전략을 표현하는 일반 실행 계약은 없다.
- 자금관리 정책이 요구할 수 있는 현재 timeframe은 strategy timeframe과 일봉이다. Turtle의
  일봉 `N`은 전략 입력이 아니라 정책 입력이다.
- `DecisionIntent`에는 손절, 익절, 수량과 leverage 필드가 없다. 보호가격과 수량과 요청
  leverage는 자금관리 정책이 소유한다.
- 현재 실행은 전량 청산 경로를 제공하지만 부분 익절과 실행 가능한 트레일링을 제공하지 않는다.
  트레일링 모듈은 예약 위치이고 matcher는 관련 주문을 거부한다.
- 현재 저장소에는 실행 능력을 한 곳에서 조회하는 `capabilities.py`가 없다.
- 현재 `.claude/agents/strategy-architect.md`는 읽기 전용 설계와 진단 Agent다. 이 문서가 요구하는
  전략 구현 Agent나 독립 계산 검증 Agent를 대신하지 않는다.
- 인수 시험 문서 두 편은 `0dd26a2`가 있는 별도 브랜치에는 존재하지만 현재 브랜치에는 없다.
- 신규 전략 적재의 기반인 `StrategyBase`, 허용 목록과 카탈로그 맞춰 보기는 구현되었지만 Web
  API는 아직 `VesselReference`를 직접 참조하므로 화면 완료 경로는 일반화되지 않았다.
