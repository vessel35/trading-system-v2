# 전략과 정책의 사실을 도구로 내주고 등록 산출물을 선언에서 만든다

이 문서는 전략 작성 절차가 딛는 사실을 도구로 내주고, 등록 행의 **선언에서 나오는 부분**을
만들어 내는 방법을 정한다. **운영 데이터베이스에 등록 행을 쓰는 일은 넣지 않는다**(사용자
확정, 7장).

절차 자체는 `.claude/skills/author-strategy/SKILL.md`가 계속 소유한다. **skill은 무엇을 언제
판단할지를 갖고, 여기서 만드는 것은 그 판단이 딛는 사실을 갖는다.**

**이 문서는 설계 검토를 한 번 받아 고쳐진 판이다.** 검토가 찾아낸 내 사실 오류 넷과 그 정정은
11장에 모아 두었다. 그 가운데 둘은 도구의 이름과 약속을 바꿀 만큼 컸다.

## 1. 지금 무엇이 아쉬운가

**사실이 프롬프트를 거쳐 전달된다.** skill은 registry에 물어보라며 파이썬 조각을 적어 두고,
읽는 쪽이 그것을 돌려 결과를 말로 옮긴다. 옮기는 자리마다 틀릴 수 있고, **틀려도 아무것도
멈추지 않는다.** 이번 세션에 능력 문장을 네 번 틀렸고 전부 검토가 잡았다.

**구현자가 바뀌었다.** 2026-08-11부터 구현은 Codex가 한다. 지금 구조에서는 능력 목록과 두
registry의 내용이 내 프롬프트를 통해서만 Codex에 닿는다.

**등록 행에서 선언과 겹치는 부분을 손으로 베낀다.** 규범 4.6은 코드 선언과 등록 행이 같아야
한다고 요구하지만, 지금 어긋남을 잡는 방식은 **실행 거부**다. 어긋나게 쓰는 것 자체를 막지는
못하고 실행할 때가 되어야 드러난다.

## 2. 코드에서 확인한 사실

### 2.1 등록 행이 담는 것과 클래스가 선언하는 것

`strategy_registry`는 열 열넷, `money_management_registry`는 열 열하나다. 넷으로 갈린다.

**선언에서 그대로 나오는 것.** 전략은 `strategy_id`와 `class_name`과 `module_path`와
`strategy_version`과 `supported_timeframes`와 `required_indicators_json`과 `min_history`
일곱이다. 정책은 `mode`와 `class_name`과 `module_path`와 `policy_version`과 `settings_names`
다섯이다.

**사람이 정하는 표시 정보 둘.** `display_name`과 `description`이다.

**운영이 소유하는 스위치 둘.** `is_active`와 `is_deprecated`이며, 규범 6.4가 "켜고 끄는 것은
코드가 아니라 이 두 열이 맡는다"고 정했다.

**데이터베이스가 채우는 둘.** `registered_at`과 `updated_at`이다.

**여기에 전략 쪽 한 열이 더 있고, 그것이 검토가 잡은 자리다.** `default_params_json`은 클래스
기본값의 사본이 아니라 **운영자가 정하는 시작값 제안**이다. `services/web-api/web_api/repository.py`는
선언을 읽을 수 있을 때 `StrategyConfig.json_schema`에서 기본값을 새로 만들고, **읽지 못할 때만**
등록 행의 값을 쓴다. 그러므로 parameter schema를 그대로 복사해 넣으면 사람이 정해 둔 시작값을
덮는다. **이 열은 선언에서 나오지 않는다.**

### 2.2 런타임은 등록 표에 쓰지 않는다

`services/signal-service/signal_service/infrastructure/strategy_registry.py`와
`services/backtest-service/backtest_service/adapters/strategy_registry.py`의 `register`가 둘 다
`PermissionError`를 낸다. 규범 6.4는 운영자가 배포 전에 init SQL을 적용한다고 정하고, 로드맵
3-1 계획서 11장은 운영 중 임의 카탈로그 쓰기 API를 범위 밖으로 못박았다.

### 2.3 등록 행은 정책을 만들지 않는다

`core_lib/money_management/registry.py`의 `create`는 **발견된 정책 mapping**과 제출된 설정으로
정책을 만든다. 등록 행은 고를 수 있는지를 정할 뿐 생성의 원천이 아니다. 전략 쪽은 다르다 —
`AdapterManager.create`가 등록 행을 조회해 신원과 선언을 대조한 뒤 클래스를 만든다.

### 2.4 대조 함수 둘은 데이터베이스를 모르지만 받는 것이 다르다

`reconcile_money_management_availability`는 등록 행의 나열을 그대로 받는다. 반면
`reconcile_strategy_registries`는 **`StrategyRegistry` 포트와 발견 registry를 받는다.** 그래서
만들어 낸 전략 행을 먹이려면 **인메모리 `StrategyRegistry` 어댑터가 하나 필요하다.**

### 2.5 실행이 거부하는 것 가운데 등록 대조가 보지 않는 것

`AdapterManager.create`가 보는 것은 카탈로그 조회와 수명주기, 클래스 신원, 선언 대조,
parameter 해석, 생성자다. **그 밖의 거부는 뒤에서 일어난다.** 실행 timeframe이 지원 목록에
있는지, 선언한 series 조합이 registry에 등록되어 있는지, 짝 series가 요구하는 두 번째 종목이
있는지, 정책이 변동성 입력을 정확히 하나 선언했는지, 정책 요구 timeframe의 값이 실제로
준비되는지, 라이브 신호가 요구하는 정책 capability가 있는지가 그렇다. **`DecisionIntent`를
선언하고 `TradingSignal`을 돌려주는 위반은 첫 판단을 받아 본 뒤에야 드러난다.**

이 거부들은 실행 설정과 시장 입력이 있어야 부를 수 있다. **등록만 가지고는 재현할 수 없다.**

### 2.6 정책 설정 이름의 제약은 데이터베이스 없이도 판정된다

표는 `settings_names`가 null 없는 정렬된 중복 없는 배열이기를 요구한다. `policy_settings`를
정렬하면 그 모양이 그대로 나오고, `names == sorted(set(names))`로 확인할 수 있다. **데이터베이스가
있어야만 알 수 있는 것이 아니다.** 데이터베이스 검사가 따로 갖는 값은 SQL 자체의 유효성과
형 변환과 길이 제한과 CHECK 통과와 왕복 일치다.

### 2.7 패턴은 채택 근거를 항목마다 갖고 있지 않다

`IndicatorSpec`에는 `pinned_impl`이 있어 이식한 표준의 절을 낼 수 있다. 그러나 `PatternSpec`이
가진 것은 공통 `version` 하나이며 항목마다의 채택 근거가 없다. **패턴의 정의가 문서의 뜻과
같은지는 여전히 계산 표준을 읽어야 한다.**

### 2.8 이 저장소에는 자체 도구 진입점도 MCP 서버도 없다

`.mcp.json`에 등록된 다섯은 모두 외부 npx 패키지다. 그리고 저장소 `.venv`에는 `mcp`도
`fastmcp`도 설치되어 있지 않다. **MCP 서버를 만들면 의존성이 하나 늘고, 파일을 고친 뒤 서버를
다시 띄우지 않으면 옛 import 결과를 계속 답한다.**

## 3. 무엇을 만드는가

**사실 모듈 하나와 그 위에 얹는 껍데기 둘이다.** 계산은 전부 import 가능한 모듈에 두고,
명령줄 진입점과 MCP 서버가 같은 모듈을 부른다. **skill이 가리키는 것은 명령줄 쪽이다** —
절차가 떠 있는 서버에 기대지 않게 하기 위해서다.

도구는 여섯이다.

**읽는 것 넷.**

1. `capabilities(id?)` — `core_lib.capabilities`의 항목을 그대로 낸다.
2. `series(name?)` — 지표 조합과 패턴을 이름·parameter·warm-up과 함께 낸다. **채택 근거는
   지표에만 실린다**(2.7). 패턴에는 계산 표준을 읽어야 한다는 것을 함께 낸다.
3. `deployed(kind)` — 발견된 전략 또는 정책과, 불러오지 못한 파일과 그 사유를 낸다.
4. `declaration(kind, id)` — 그 클래스가 선언한 것을 낸다. 전략이면 metadata와
   `StrategyProfile`과 parameter schema, 정책이면 설정 이름과 기본값과 판과 두 capability와
   **그 정책이 요구하는 단 하나의 입력**이다.

**등록을 돕는 것 둘.**

5. `registration_sql(kind, id, display_name, description, is_active, default_params?)` —
   선언에서 나오는 열을 채우고 나머지를 인자로 받아 멱등 SQL을 만든다. 규칙은 4장에 있다.
6. `catalog_precheck(kind, id, row?)` — **등록 신원과 선언 대조만** 본다. 이름을 그렇게 붙인
   이유는 5장에 있다.

**일곱째 도구는 두지 않는다.** 일회용 데이터베이스 검사는 도구가 아니라 **표시가 붙은
시험**으로 둔다(6장).

### 3.1 어디에 두는가

**`services/trading-plugins/trading_plugins/` 아래에 둔다.** 사실 모듈이 `core_lib`과 발견
결과를 함께 보아야 하는데, `core_lib`은 위 계층을 import할 수 없고 이미 두 쪽을 다 보는
패키지가 여기뿐이다. 새 패키지를 하나 만들면 `pyproject`와 설치와 검사 배선이 모듈 하나 때문에
늘어난다.

**발견이 훑는 자리와 섞이지 않는다.** 발견은 `trading_plugins.strategies`와
`trading_plugins.money_management` 두 하위 패키지만 훑으므로(규범 6.3), 최상위에 둔 모듈은
전략이나 정책으로 오인되지 않는다.

### 3.2 명령의 모양

`python -m trading_plugins.facts <이름> [인자]` 하나로 부르고 **결과를 JSON으로 표준 출력에
낸다.** 이름은 도구 이름과 같다. 사람이 읽을 형식을 따로 두지 않는다 — 읽는 쪽이 사람이든
Agent든 같은 값을 보아야 한다.

**실패는 형식이 있는 오류로 낸다.** 종료 코드가 0이 아니고, 표준 출력에 `error` 하나를 담은
JSON을 낸다. 예외 문자열을 그대로 흘리지 않는다.

## 4. 등록 SQL을 만드는 규칙

**선언에서 나오지 않는 값은 인자로 받고 지어내지 않는다.** `display_name`과 `description`은
필수 인자다. **`description`을 클래스 docstring으로 채우지 않는다** — 그것은 사실 조회가 아니라
등록 문구를 고르는 일이고, skill이 "없는 값을 발명하지 않는다"고 정한 자리에 걸린다.
`default_params`도 인자이며, 주지 않으면 그 열을 빈 객체로 둔다.

**`is_active`는 인자로 받되 기본값을 두지 않는다.** 이것이 스위치이므로 기본값을 두면 도구가
운영 결정을 대신하게 된다.

**충돌 시 갱신에서 수명주기 열 둘을 뺀다.** 기존 `02-register-vessel-reference.sql`은
`is_active`와 `is_deprecated`까지 `excluded` 값으로 덮는데, **그 모양을 그대로 만들면 폐기된
행에 다시 적용할 때 폐기가 조용히 풀린다.** 만들어 내는 문장은 선언에서 나오는 열과 표시 정보와
`default_params_json`만 갱신하고, **수명주기 변경은 별도 운영 문장으로 남긴다.** 새 행을 넣을
때의 초기값으로만 `is_active`를 쓴다.

**직렬화를 못박는다.** 정책 설정 이름은 정렬하고 빈 배열에는 형을 명시한다. 전략의 지원
timeframe 순서는 런타임 대조가 그대로 견주므로 선언 순서를 보존한다. series 선언은 **생성기가
정한 하나의 순서**로 적는다 — 런타임은 순서를 무시하지만 JSONB 배열 비교는 순서를 구분하므로,
정하지 않으면 같은 선언이 매번 갱신을 일으킨다. JSON은 key 순서를 고정하고 유한하지 않은 수를
거부한다. 표시 정보와 경로와 JSON 안의 따옴표는 안전하게 literal 처리한다. `IS DISTINCT FROM`
양쪽의 열 목록은 실제 갱신 열과 정확히 같아야 한다.

**`module_path`는 클래스에서 읽되 발견된 두 패키지 안인지 확인한다.** 등록 행의 경로는 적재에
쓰이지 않지만 대조에 쓰이므로 틀리면 실행이 거부된다.

## 5. 사전 점검이 무엇을 증명하고 무엇을 증명하지 않는가

**이름을 `catalog_precheck`로 좁힌다.** 앞선 판에서 나는 이것이 "런타임이 거부할 것을 다
잡는다"고 적었는데 **거짓이다.** 2.5가 적은 대로 실행 timeframe과 series 해석과 정책 입력과
라이브 capability는 실행 설정과 시장 입력이 있어야 부를 수 있고, 반환 형 위반은 첫 판단을
받아야 드러난다.

**그래서 이 점검이 증명하는 것을 그대로 적는다.** 만들어 낸 행이 클래스와 같은 신원을
가리키는지, 선언한 series와 최소 이력과 지원 timeframe이 등록 값과 같은지, 수명주기가 실행을
막지 않는지, 그리고 전략이면 그 행으로 매니저가 클래스를 만들 수 있는지다. 정책이면 발견
결과와 등록 행이 맞아 고를 수 있는 상태인지다.

**증명하지 않는 것도 그대로 적는다.** 이 점검을 통과한 전략이 실행에서 거부될 수 있다. 그
거부는 실행 설정이 정해진 뒤에 일어나며, **런타임의 검사를 이 도구 안에 복제하지 않는다** —
복제하면 두 곳이 갈라지고 어느 쪽이 맞는지 판정할 근거가 없어진다.

**대조는 런타임이 쓰는 그 함수를 그대로 부른다.** 전략 쪽은 인메모리 `StrategyRegistry`
어댑터를 하나 두어 만들어 낸 행을 먹이고(2.4), 정책 쪽은 행 나열을 그대로 넘긴다.

## 6. 일회용 데이터베이스 검사는 시험으로 둔다

**임의 DSN을 받는 도구로 두지 않는다.** 이름이 일회용처럼 보이는지로는 운영 데이터베이스를
가려낼 수 없고, 받은 DSN에 DDL을 돌리고 데이터베이스를 지우는 도구는 이름 위장과 잘못된
자격증명에 그대로 노출된다. 사용자 승인을 받았는지를 서버가 스스로 증명할 계약도 없다.

**대신 저장소의 표시가 붙은 시험으로 둔다.** 시험이 **자기가 만든 임시 schema 안에서만** 표를
세우고 만들어 낸 문장을 적용해 제약을 통과하는지와 다시 읽은 값이 같은지를 본다. 끝나면 자기가
만든 것만 지운다. 저장소에 이미 있는 `integration` 표시와 같은 방식으로 **명시적으로 고르지
않으면 건너뛴다.** DSN은 결과와 오류에 싣지 않는다.

## 7. 하지 않는 것

- **운영 데이터베이스에 등록 행을 쓰지 않는다.** 사용자가 정한 범위다.
- **런타임의 쓰기 거부를 풀지 않는다.**
- **런타임의 실행 검사를 도구 안에 복제하지 않는다.**
- **수명주기를 도구로 바꾸지 않는다.** 활성화와 폐기는 운영 문장이다.
- **능력 목록을 다시 쓰지 않는다.** 실어 나르기만 한다.
- **재고를 도구 안에 적지 않는다.** 지표와 패턴과 정책 mode는 언제나 조회 결과다.
- **전략을 만들지 않는다.**
- **legacy 전략을 목표 계약으로 가정하지 않는다.** `StrategyMetadata.decision_contract`의
  기본값은 여전히 `TradingSignal`이고 매니저는 정책 없는 legacy 전략을 허용한다.

## 8. skill과 어떻게 이어지는가

`author-strategy`의 "먼저 읽는 것"에서 파이썬 조각을 걷어내고 명령줄 호출로 바꾼다. 절차의
문장은 그대로다 — **재고는 조회하고 능력은 목록에서 읽으라는 규칙이 바뀌는 것이 아니라, 그
조회가 하나의 명령이 되는 것이다.**

**MCP 서버가 없어도 절차가 돌아야 한다.** 그래서 skill이 가리키는 것은 명령줄이고, MCP는 같은
모듈 위의 또 다른 껍데기다.

## 9. 드리프트를 어떻게 막는가

**도구가 내주는 값이 원본과 같은지 검사한다.** `capabilities`가 내는 것이
`PLATFORM_CAPABILITIES`와 항목 대 항목으로 같은지, `series`가 내는 것이 두 registry의 내용과
같은지 본다. 값을 손질하기 시작하면 이 검사가 깨진다.

**만들어 낸 SQL이 기존 등록 파일과 의미가 같은지 회귀로 붙든다.** 다만 `VesselReference` 한
건으로는 부족하다. 따옴표가 든 표시 정보, 비어 있지 않은 parameter 기본값, 여러 timeframe,
정책의 설정 배열, 그리고 **수명주기 열이 갱신에서 빠졌다는 것**을 각각 확인한다.

**떠 있는 서버가 낡는 것은 검사가 잡지 못한다.** 새 프로세스에서 값을 견주는 검사는 변환이
어긋나는 것만 잡는다. 그래서 skill이 명령줄을 가리키고, MCP 문서에 **파일을 고치면 서버를
다시 띄운다**를 적는다.

## 10. changeset 분리와 순서

1. **사실 모듈과 명령줄 진입점.** 읽는 도구 넷과 드리프트 검사다.
2. **skill 연결.** `author-strategy`의 조회 자리를 명령으로 바꾼다. 1이 끝나면 바로 할 수 있고
   등록 쪽을 기다릴 이유가 없다.
3. **등록 문장 생성과 `catalog_precheck`.** 4장의 직렬화 규칙과 9장의 회귀를 함께 넣는다.
4. **일회용 데이터베이스 시험.** 표시를 붙이고 명시적으로 고를 때만 돌게 한다.
5. **MCP 껍데기.** 같은 모듈 위에 얹고 `.mcp.json`에 등록한다. 의존성이 하나 느는 자리이므로
   마지막에 둔다.

## 11. 설계 검토가 바로잡은 것

**아래 넷은 내가 틀리게 적었던 것이고, 코드에서 확인해 바로잡았다.**

1. **`default_params_json`이 클래스 선언에서 나온다고 적었다.** 그것은 운영자가 정하는 시작값
   제안이고, Web API는 선언을 읽을 수 있을 때 schema에서 기본값을 새로 만들며 등록 행은
   읽지 못할 때의 대비책이다. 복사해 넣으면 사람이 정한 값을 덮는다.
2. **데이터베이스 없는 점검이 런타임 거부를 다 잡는다고 적었다.** 잡지 못한다. 이름을
   `catalog_precheck`로 좁히고 증명하는 것과 못 하는 것을 5장에 나열했다.
3. **기존 등록 SQL과 같은 모양으로 만들자고 적었다.** 그 모양은 충돌 시 수명주기 열까지
   덮으므로 **폐기된 행을 조용히 되살린다.** 갱신에서 두 열을 뺐다.
4. **일회용 데이터베이스 검사를 임의 DSN을 받는 도구로 두려 했다.** 이름만으로 대상을
   가려낼 수 없고 승인을 증명할 계약도 없다. 도구를 없애고 표시가 붙은 시험으로 옮겼다.

**표현이 부정확했던 것도 셋이다.** 열을 "셋이 나오지 않는다"고 적고 넷을 열거했으며, 두 표의
열 수를 세지 않았다. `reconcile_strategy_registries`에 행을 "그대로 먹인다"고 적었으나 그것은
포트를 받으므로 인메모리 어댑터가 필요하다. 정책 설정 이름 제약을 데이터베이스만 잡을 수
있다고 적었으나 정렬과 중복은 글자만으로 판정된다.

**그릇에 대한 지적도 받아들였다.** `.venv`에 MCP 의존성이 없고 떠 있는 서버는 옛 import
결과를 답할 수 있으므로, **명령줄을 먼저 만들고 MCP를 그 위에 마지막으로 얹는다.** 만드는
것의 끝은 같고 순서와 skill이 기대는 대상이 달라졌다.

## 12. 무엇을 만족하면 닫힌 것인가

- 사실 모듈이 있고 명령줄이 그것을 JSON으로 낸다. `capabilities`와 `series`가 내는 값이
  원본과 항목 대 항목으로 같음을 검사가 확인하며, 값을 손질하면 그 검사가 깨진다.
- `registration_sql`이 `VesselReference`에서 만든 문장이 기존 등록 파일과 **선언·표시 열에
  대해** 의미가 같고, **수명주기 열이 갱신 목록에 없다.** 폐기된 행에 다시 적용해도 폐기가
  풀리지 않는 것을 확인한다.
- `default_params`를 주지 않으면 그 열이 비고, 주면 그 값이 그대로 실린다. 클래스 기본값이
  조용히 실리지 않는다.
- 선언과 어긋나는 행을 일부러 만들어 넣으면 `catalog_precheck`가 그 상태를 이름으로 낸다.
- **`catalog_precheck`가 증명하지 않는 것이 문서와 도구 설명에 적혀 있다.** 실행 timeframe과
  series 해석과 정책 입력과 라이브 capability가 그 뒤의 검사임을 밝힌다.
- 일회용 데이터베이스 시험이 **표시를 명시적으로 골랐을 때** 돌고 통과한다. 기본 pytest
  실행에서는 건너뛴다는 것도 함께 보인다.
- 어떤 도구도 운영 데이터베이스에 쓰지 않는다. 임의 DSN을 받는 도구가 없다.
- `author-strategy`가 명령줄을 가리키고, MCP 서버 없이도 같은 값을 얻는다.
- 저장소 뿌리에서 `.venv/bin/python -m pytest services -q`가 exit 0이고, `ruff check`와
  `ruff format --check`가 exit 0이며, 바뀐 서비스 디렉터리 안에서 돌린 mypy가 exit 0이다.
  일회용 데이터베이스 시험은 그 표시를 골라 따로 돌린 결과를 함께 보인다.
- 기존 전략 판단과 Evidence와 등록 행이 달라지지 않는다.
