# 전략 적재 경로와 전략 구현체 배치 설계

이 문서는 전략 적재와 카탈로그 맞춰 보기의 최종 설계이며, 기반 클래스와 허용 목록과 맞춰 보기는 구현되었지만 화면 연계와 전략 구현체의 별도 패키지 이동은 아직 끝나지 않았다.

## 1. 목적과 범위

이 설계는 배포된 전략 클래스를 서비스가 어떻게 적재하고, 외부 카탈로그와 코드가 어긋난 상태를
어떻게 드러내며, 앞으로 늘어날 전략 구현체를 어디에 둘지를 정한다. 전략의 진입과 청산 edge,
자금관리 수식, 주문 실행 방식은 바꾸지 않는다.

현재 `VesselReference`는 목표 계약인 `DecisionIntent`를 반환하고 Engine은
`MoneyManagementPolicy`를 조합한다. 다만 규범 Protocol인 `StrategyAdapter`는 이행 기간의
legacy `TradingSignal`도 계속 허용한다. 이 설계의 적재 경로는 두 계약을 모두 수용하되, 신규
전략은 `DecisionIntent` 계약을 따라야 한다.

## 2. 적재의 보안 경계

외부 카탈로그의 `module_path`를 그대로 import하지 않는다. 카탈로그는 운영 데이터의
등록처이지 코드 배포 수단이 아니다. 카탈로그 행을 쓸 수 있는 주체가 임의의 모듈을 실행하게
해서는 안 된다.

배포 가능한 전략 클래스는 명시적인 `STRATEGY_ALLOWLIST`에 둔다. 허용 목록은 전략 id와 이미
import된 클래스 객체를 잇고, 각 소비자는 `build_strategy_registry()`로 격리된
`InProcessStrategyRegistry`를 만든다. 현재 backtest-service와 signal-service는 이 경로를
사용한다.

적재 조립은 서비스를 실행하는 쪽이 소유한다. `core_lib`은 `StrategyRegistry` 포트, in-process
레지스트리, `AdapterManager`, 허용 목록과 맞춰 보기 규칙을 제공하지만 외부 카탈로그가 지시한
코드를 동적으로 가져오지 않는다.

## 3. 단건 생성과 전체 맞춰 보기

단건 생성은 `AdapterManager.create()`가 담당한다. 매니저는 외부 카탈로그에서 행을 읽고,
in-process 레지스트리에서 허용된 클래스를 찾은 뒤 다음 사실을 검사한다.

1. 카탈로그의 전략 id가 요청한 id와 같아야 한다.
2. 카탈로그의 전략은 활성 상태이며 폐기 상태가 아니어야 한다.
3. `class_name`과 `module_path`가 허용 목록의 클래스 신원과 같아야 한다.
4. `min_history`, `supported_timeframes`, `required_indicators_json`이 Adaptee 선언과 같아야 한다.
5. 검사를 통과한 뒤에만 파라미터 스키마를 해석하고 인스턴스를 만든다.

단건 생성과 별도로 `AdapterManager.reconcile_catalog()`가 카탈로그 전체와 허용 목록 전체를
맞춰 본다. 정상 항목은 결과에서 빼고 다음 다섯 상태만 반환한다.

| 상태 | 확인된 의미 | 실행과 표시 원칙 |
|---|---|---|
| `catalog_only` | 카탈로그에는 행이 있지만 배포 허용 목록에는 클래스가 없다. | 이 배포본에서는 실행할 수 없다고 표시한다. |
| `allowlist_only` | 배포 허용 목록에는 클래스가 있지만 카탈로그에 등록 행이 없다. | 등록되지 않은 전략으로 표시하고 실행 대상으로 내리지 않는다. |
| `identity_mismatch` | 양쪽에 같은 id가 있지만 클래스 이름이나 모듈 경로가 다르다. | 어느 쪽이 낡았는지 추측하지 않고 실행을 거부한다. |
| `inactive` | 클래스 신원은 맞지만 카탈로그가 비활성으로 표시한다. | 목록에는 상태를 드러내되 선택할 수 없게 한다. |
| `deprecated` | 클래스 신원은 맞지만 카탈로그가 폐기 상태로 표시한다. | 폐기 사실을 드러내고 신규 실행을 허용하지 않는다. |

맞춰 보기는 한 전략에 가장 근본적인 상태 하나만 부여한다. 구성원 차이가 신원 차이보다 먼저
판정되고, 신원 차이가 lifecycle 상태보다 먼저 판정되며, 폐기 상태는 비활성 상태보다 먼저
판정된다. 이 우선순위 덕분에 같은 id에 상충하는 표시가 여러 개 생기지 않는다.

## 4. 선택적 전략 기반 클래스

`StrategyAdapter` Protocol이 규범 계약이다. `StrategyBase`는 Protocol을 만족하기 쉽게 만든
선택적 추상 기반 클래스이며, 모든 전략이 이를 상속해야 하는 것은 아니다.

기반 클래스는 `get_metadata()`, `get_parameter_schema()`, `analyze()`를 추상 메서드로 두고,
선언한 지표와 패턴 값을 공통 `series_key()`로 읽는 `series_value()`를 제공한다. 상태 슬롯은
두지 않는다. 계좌 조회, 보호가격, 수량, leverage, 주문 생성과 입출력도 제공하지 않는다.

현재 `VesselReference`는 기반 클래스를 상속하지 않고 `StrategyAdapter`를 구조적으로 만족한다.
그러므로 기반 클래스 도입은 기존 전략의 동작이나 상속 구조를 바꾸지 않는다.

## 5. 등록 산출물과 읽기 전용 운영 경계

신규 전략 changeset은 다음 산출물을 함께 가져야 한다.

1. 전략 구현과 메타데이터를 추가한다.
2. 같은 전략 id와 클래스를 `STRATEGY_ALLOWLIST`에 추가한다.
3. 카탈로그의 모든 필드를 채운 판이 매겨진 멱등 SQL 등록 행을 추가한다.
4. 코드 선언과 등록 행을 사전에 대조하는 검사를 추가한다.
5. backtest-service와 signal-service가 같은 허용 목록으로 그 전략을 생성하는지 확인한다.

서비스의 런타임 카탈로그 어댑터는 읽기 전용으로 유지한다. 등록 SQL을 changeset에 포함하는
것과 운영 중 임의 쓰기 API를 허용하는 것은 다른 문제다. 이 설계는 운영 등록 API를 만들지
않는다.

현재 데이터베이스 프로비저닝은 v1 데이터를 읽거나 복사하지 않고 새 v2 데이터베이스와
카탈로그를 구성한다. 검증도 legacy 데이터가 없는 상태와 `vessel-reference` 등록 한 건을
확인한다. 따라서 이전 설계가 전제로 삼았던 영속 볼륨의 오래된 등록 행을 위한 별도 순방향
migration은 현재 범위의 위험이 아니다. 등록 신원이 바뀌는 changeset은 정본 init SQL을 같은
변경에서 고치고 재구성된 v2 데이터베이스를 기준으로 검증한다.

## 6. Web API와 화면의 남은 설계

현재 Web API는 한 파일에서 `VesselReference`를 직접 참조한다. 데이터베이스 행을 보강할 때
전략 id를 `vessel-reference`와 비교하고, 카탈로그가 비었을 때도 코드에서 같은 전략을 다시
만든다. 이 경로는 허용 목록과 다섯 상태를 사용하지 않으므로 아직 이 설계의 끝점에 닿지
않았다.

Web API는 허용 목록과 카탈로그 맞춰 보기 결과를 사용해 다음 정보를 내려야 한다.

1. 응답은 전략이 실제로 실행 가능한지와 실행할 수 없다면 그 이유를 포함해야 한다.
2. 응답은 실제 `StrategyProfile`, 지원 정책, 기본 정책과 resolved 기본 설정을 포함해야 한다.
3. 비활성, 폐기, 카탈로그 전용, 허용 목록 전용과 신원 불일치를 서로 구분해야 한다.
4. 화면은 실행 가능한 전략만 선택하게 하고, 목록이 비었다는 이유로 고정 전략을 다시 만들지
   않아야 한다.
5. 응답 모델 변경은 OpenAPI와 생성된 프런트 타입에 함께 반영되어야 한다.

화면 노출은 신규 전략 완료 조건의 일부지만, 이 문서는 UI의 구체적인 배치나 표현 문구를 새로
정하지 않는다.

## 7. 전략 구현체의 배치

현재 전략 구현체는 `services/core-lib/core_lib/strategy/adaptees/`에 있다. 안정적인 플랫폼
계약과 계속 늘어나는 전략 구현체를 다른 배포 단위로 나누는 책임 경계에는 이점이 있지만,
별도 패키지로 옮길지는 아직 사용자 판단이 남아 있다.

별도 패키지를 선택하면 `StrategyAdapter`, 설정 해석, in-process 레지스트리,
`AdapterManager`, 프로파일과 카탈로그 포트는 `core_lib`에 남고, `VesselReference`와 앞으로
추가할 Adaptee만 새 패키지로 이동한다. 이동은 전략의 판단이나 자금관리 결과를 바꾸지 않아야
한다.

이동 비용은 실제로 넓다. 새 패키지 메타데이터와 타입 표식, 공개 export, 구현체의 상대 import,
세 소비자의 의존 선언과 editable 경로, 저장소 설치 목록, CI의 mypy 대상과 테스트 소유권을
함께 바꿔야 한다. `core-lib==0.2.0`을 선언하는 서비스는 backtest-service, signal-service,
web-api와 wallet-service의 네 곳이지만 전략 패키지를 직접 소비할 곳은 앞의 세 곳이다.

현재 저장소에는 패키지를 게시하는 CI가 없고 개발 의존성은 로컬 editable 경로로 연결된다.
따라서 별도 패키지의 판을 독립적으로 올리면 배포 마찰이 줄어든다는 이점은 아직 입증되지
않았다. 패키지 이동을 선택하기 전에 정확한 판 고정과 호환 범위 가운데 어느 의존 정책을 쓸지
확정해야 한다.

## 8. 구현 순서

기반 작업은 이미 완료되었다. `e1fd478`에서 선택적 `StrategyBase`, 명시적 허용 목록, 두
서비스의 공통 레지스트리 조립, 다섯 상태 맞춰 보기와 단위 검사가 들어왔다.

남은 작업은 다음 순서를 따른다.

1. Web API가 직접 `VesselReference`를 참조하는 경로를 허용 목록과 맞춰 보기 결과로 바꾼다.
2. 실행 가능 여부와 사유를 API와 화면과 생성 타입에 반영한다.
3. 신규 전략 등록 절차와 읽기 전용 사전 점검을 완성한다.
4. 전략 구현체의 별도 패키지 이동은 사용자 결정과 의존 정책 확정 뒤에 별도 changeset으로
   수행한다.

전략 edge 변경, 자금관리와 실행 리팩터링은 이 순서에 섞지 않는다. manual 호환 정책과 기존
기본값도 그대로 보존한다.

## 9. 완료 기준

- 두 실행 서비스와 Web API가 같은 허용 목록을 사용해야 한다.
- 카탈로그의 `module_path`를 동적으로 import하는 경로가 없어야 한다.
- 다섯 맞춰 보기 상태가 API와 화면에서 서로 다른 실행 가능 상태로 드러나야 한다.
- 신규 전략의 코드, 허용 목록과 등록 SQL이 같은 changeset에 있어야 한다.
- 등록과 코드의 신원 및 선언 불일치가 실행 전에 검출되어야 한다.
- 구현체를 이동하기로 했다면 의존 선언, 설치 목록, 타입 검사와 테스트 소유권까지 함께
  이동해야 한다.
- 기존 전략 판단, manual 호환 결과, 기본 정책과 Evidence가 달라지지 않아야 한다.
- 관련 pytest, mypy와 ruff가 통과하고 건너뛴 검사 수를 함께 보고해야 한다.

## 10. 열려 있는 결정

전략 구현체를 `core_lib`에 계속 둘지 별도 패키지로 옮길지는 결정되지 않았다. 별도 패키지를
선택하는 경우에도 이동은 허용 목록과 화면 연계를 완성하는 작업과 분리한다.

## 11. 검토에서 바로잡힌 사실

- `AdapterManager`는 이미 카탈로그 행과 in-process 클래스를 연결하고 클래스 신원과 선언된
  이력을 검사한다. 새로 필요했던 것은 단건 연결이 아니라 전체 목록의 상태 맞춰 보기였다.
- 카탈로그에만 있는 전략은 클래스 조회에서 실패하므로 조용히 적재되는 상태가 아니다.
- 직접 결합은 backtest runner와 signal main 외에도 Web API의 행 보강과 fallback, 등록 seed와
  관련 검사에 걸쳐 있다. 현재 두 실행 서비스의 직접 등록은 공통 허용 목록으로 정리되었지만
  Web API의 직접 참조는 남아 있다.
- `core-lib==0.2.0`은 네 서비스가 선언한다. 전략 구현체를 직접 쓰는 서비스는
  backtest-service, signal-service와 web-api의 세 곳이다.
- 구현체 이동은 카탈로그의 `module_path`만 바꾸는 작업이 아니다. import, 공개 export, 의존
  선언, editable 설치, mypy 대상과 테스트 소유권이 함께 바뀐다.
- `RunConfig`와 sweep의 Vessel 식별자 분기는 legacy manual 호환 경계다. 이 분기를 허용 목록
  일반화 대상으로 취급하지 않는다.
- v2 데이터베이스는 legacy 행을 이관하지 않는 새 프로비저닝으로 재구성되었다. 오래된 등록
  행을 위한 별도 migration을 구현체 이동의 선행 조건으로 두지 않는다.
