# 3-1 실행 계획: 신규 전략 개발 기반과 Agent 워크플로

이 문서는 3-1 단계의 최종 실행 계획이며, 전략 기반 클래스와 허용 목록과 카탈로그 맞춰 보기는 구현되었지만 정책 정합, 등록 사전 점검, 공통 계약 검사, 실행 능력 목록과 Agent 워크플로는 아직 완료되지 않았다.

## 1. 단계의 목표

3-1은 특정 전략을 출시하는 단계가 아니다. 사람이 쓴 전략 기술 문서를 플랫폼 정책을 지키는
전략으로 옮기고, 등록하고, 화면에서 실행하고, 계산을 독립 검증하는 반복 가능한 개발 기반을
만드는 단계다.

단계의 최종 산출물은 다음과 같다.

1. canonical contract와 전략 개발 skill이 지표와 패턴을 포함하는 계열 정책을 정확히 설명해야
   한다.
2. 신규 전략을 두 실행 서비스가 적재하고 Web API와 화면이 실행 가능 상태를 보여야 한다.
3. 전략 등록 절차와 실행 전 사전 점검이 있어야 한다.
4. 허용 목록 전체에 적용되는 공통 전략 계약 검사가 있어야 한다.
5. 신규 전략의 계산 검증 방침과 독립 verifier가 있어야 한다.
6. 실행 능력 목록을 근거로 구현 가능성을 판정하는 author Agent 워크플로가 있어야 한다.

## 2. 현재 출발점

현재 지표 레지스트리에는 91개 조합과 88개 이름이 있고 패턴 레지스트리에는 61개 조합과 61개
이름이 있다. 패턴은 `required_indicators`라는 역사적 이름의 선언에 지표와 함께 들어가지만,
실행 시에는 지표 레지스트리와 패턴 레지스트리로 분리해 해석된다.

현재 `VesselReference`는 목표 방식인 `DecisionIntent`를 반환하고 Engine은
`MoneyManagementPolicy`를 조합한다. `StrategyAdapter`와 Engine은 이행 기간의 legacy
`TradingSignal`도 계속 수용한다. 3-1에서 만드는 신규 전략은 목표 방식을 사용하며, manual
호환 기본값과 legacy 해석은 변경하지 않는다.

`e1fd478`에서 선택적 `StrategyBase`, 명시적 `STRATEGY_ALLOWLIST`, 두 실행 서비스의 공통
레지스트리 조립과 카탈로그 다섯 상태 맞춰 보기가 구현되었다. 반면 Web API는 아직
`VesselReference`를 직접 참조하고, 실행 가능 여부와 맞춰 보기 사유를 응답하지 않는다.

계열 정책을 canonical contract와 skill 전반에 반영한 `a542ecb`는 별도 브랜치에 존재하지만
현재 `feat/strategy-authoring-change`의 이력에는 포함되지 않았다. 따라서 이 계획에서는 통합이
끝난 것으로 간주하지 않는다.

Agent 인수 시험 문서 두 편을 저장한 `0dd26a2`도 같은 별도 브랜치에 있고 현재 브랜치에는
포함되지 않았다. Agent 워크플로 구현 전에 확정된 두 원본을 현재 이력에 통합해야 한다.

실행 능력 목록, 공통 전략 계약 검사, `strategy-author`와 `strategy-verifier`는 현재 저장소에
없다.

## 3. 계약과 skill의 계열 정합

첫 번째 갈래는 `docs/strategy-authoring-contract.md`와
`.claude/skills/develop-trading-strategies/SKILL.md`를 실제 계열 경로에 맞추는 작업이다.

계약은 한 절만 고치는 것이 아니라 전략 작성 규칙, 계열 조합, 이력 확보, 등록, Evidence, 필수
테스트와 완료 체크리스트를 함께 정합해야 한다. 다음 사실이 서로 모순 없이 들어가야 한다.

1. `required_indicators`와 `required_indicators_json`은 이름과 달리 지표와 패턴을 모두 담는다.
2. 지표와 패턴의 이름 공간은 서로소이며 이름으로 각각의 레지스트리에 분배된다.
3. 전략이 실제로 읽는 열쇠는 선언 문자열 자체가 아니라 `series_key()`가 만든 실행 열쇠다.
4. 패턴 값은 `pattern_detected`, `pattern_strength`, `pattern_direction`과
   `pattern_reliability`의 네 값을 가진다.
5. `indicator_mode`의 `all`은 모든 지표를 켜지만 패턴은 전략이 선언한 것만 켠다.
6. 일반 패턴 정책의 warm-up 근거는 `PatternSpec.min_history`다. 현재 TA-Lib 이식 패턴에서
   `lookback + 1`로 유도된 값과 일반 정책을 같은 규칙으로 쓰지 않는다.
7. 신규 전략은 `DecisionIntent`와 `MoneyManagementPolicy` 목표 방식을 사용한다.

skill의 필수 조사 경로에는 `series_resolution.py`, 공통 series 정책과 패턴 레지스트리 경로를
포함한다. skill은 canonical contract를 다시 서술하지 않고 구현 절차에서 정본을 참조해야 한다.

## 4. 실행 능력 목록

두 번째 갈래는 Agent가 코드 탐색 없이 구현 가능성을 판정할 수 있는 실행 능력 목록을 만드는
작업이다. 상세 설계는 `docs/fullspec/strategy_agent_design.md`를 따른다.

목록은 실행당 timeframe과 종목 수, 캔들 종류, 보호가격 소유권, 청산 방식, 거래 간 리스크
규칙, 계열 선언과 Evidence 경로를 포함한다. 지원하지 않는 기능도 명시하고, 정확한 집합 단언과
구조 검사로 실제 코드와 대조한다.

능력 목록은 Agent 구현보다 먼저 완료한다. Agent가 판정할 근거가 없는 상태에서 author를 만들지
않는다.

## 5. 런타임 조립과 화면 노출

세 번째 갈래는 신규 Adaptee가 실제 실행과 화면 끝점에 도달하게 하는 작업이다. 상세 설계는
`docs/fullspec/strategy_loading_and_placement_design.md`를 따른다.

이미 완료된 부분은 선택적 `StrategyBase`, 명시적 허용 목록, backtest-service와
signal-service의 공통 레지스트리 조립, `AdapterManager`의 단건 검사와 다섯 상태 맞춰 보기다.

남은 부분은 다음과 같다.

1. Web API의 직접 `VesselReference` 결합과 코드 fallback을 허용 목록과 맞춰 보기 결과로
   교체한다.
2. API는 실행 가능 여부, 불일치 사유, 실제 프로파일, 지원 정책과 기본 정책을 내려야 한다.
3. 화면은 실행 가능한 전략만 선택하게 하고 OpenAPI와 생성 프런트 타입은 응답 모델과 같아야
   한다.
4. 전략 자체가 일반 계열을 선언하지 않고 Turtle의 일봉 정책 입력만 사용하는 조합을 지원해야
   한다. 현재 Engine은 빈 `_indicator_specs`에서 `max()`를 호출하므로 이 조합을 실행할 수 없다.
5. 신규 전략 적재와 화면 노출을 실제로 확인하는 회귀 검사를 추가해야 한다.

전략 구현체를 별도 패키지로 옮기는 일은 이 갈래의 필수 전제가 아니다. 이동 여부는 사용자
결정 뒤 별도 changeset으로 다룬다.

현재 데이터베이스는 v1 데이터를 이관하지 않는 새 v2 프로비저닝으로 재구성되었다. 따라서
오래된 카탈로그 등록 행을 위한 별도 순방향 migration은 이 갈래의 선행 작업이 아니다. 신규
전략과 등록 신원 변경은 정본 init SQL과 테스트를 같은 changeset에서 갱신한다.

## 6. 등록 절차와 사전 점검

네 번째 갈래는 신규 전략 등록을 재현 가능한 절차와 검사로 만드는 작업이다.

등록 절차는 다음 질문에 답해야 한다.

1. 전략의 지원 timeframe과 최소 이력을 어떤 근거로 정하는지 설명해야 한다.
2. 선언한 지표와 패턴의 `min_history`를 각각의 레지스트리에서 어떻게 확인하는지 설명해야 한다.
3. 전략과 정책 요구를 가장 넓은 달력 구간으로 환산해 확보 이력을 어떻게 계산하는지 설명해야
   한다.
4. `strategy_registry`의 클래스 신원, 표시 이름, 설명, 전략 판, 지원 timeframe, 계열 선언,
   최소 이력, 기본 파라미터와 lifecycle 필드를 어떻게 작성하는지 설명해야 한다.
5. `StrategyProfile`의 모든 필드를 어떤 근거로 작성하는지 설명해야 한다.
6. 허용 목록, 등록 SQL과 코드 선언을 실행 전에 어떻게 맞춰 보는지 설명해야 한다.

현재 `AdapterManager`는 클래스 신원, 최소 이력, 지원 timeframe과 계열 선언을 대조한다. 전략
판, 기본 파라미터와 `StrategyProfile`까지 전부 대조한다고 넓혀 말하지 않는다.

사전 점검은 운영 쓰기 도구가 아니라 읽기 전용 검사다. 일회용 `signal_db`에 멱등 등록 SQL을
적용하고 두 서비스의 실제 매니저가 허용된 클래스를 생성하는지 확인한다. 런타임 카탈로그
어댑터의 쓰기 거부는 유지한다.

## 7. 공통 전략 계약 검사

다섯 번째 갈래는 허용 목록의 모든 전략에 자동으로 적용되는 공통 계약 검사다. 상세 설계는
`docs/fullspec/strategy_contract_suite_design.md`를 따른다.

검사는 결정성과 불변성, 정책 독립성, 시간 무결성, 금지된 의존, 선언과 접근의 일치, 방향별
진입과 청산 대응, 메서드 시그니처와 capability 정합을 다룬다. 허용 목록과 정확히 같은 방식
사례표를 요구하고, 테스트용 결함 전략으로 각 검사 장치가 실제로 실패하는지 증명한다.

공통 계약 검사 전체를 한 changeset에서 구현할지 검증 층별로 나눌지는 아직 결정되지 않았다.
나눠 구현하면 각 단계의 제공 범위와 남은 성질을 명시하고 전체 완료로 표시하지 않는다.

## 8. 계산 검증 방침

여섯 번째 갈래는 정책 준수와 별도로 전략 계산이 맞는지를 검증하는 방침을 문서화하는 작업이다.

기존 평가 임계값은 `core_lib/eval/thresholds.py`와
`docs/fullspec/50_metrics_reference.md`에서 인용하고, 신규 판단값을 도입하면 새 결정임을
명시한다.

전략 계산 검증은 다음 네 항목을 포함한다.

1. 전략이 소비한 지표와 패턴 값을 독립 기준으로 재계산한다.
2. 대표 진입과 청산 판단을 손 계산과 대조한다.
3. Evidence에서 손익, 수수료, 슬리피지, 펀딩과 보호가격을 되짚어 검산한다.
4. 구현 중 단위 검사, 등록 뒤 dry-run과 채택 전 독립 verifier에서 각각 무엇을 확인할지
   수행 시점을 정한다.

계산 검증을 통과하지 못한 전략은 성적과 무관하게 채택하지 않는다.

## 9. Agent 워크플로

마지막 갈래는 앞의 산출물을 소비하는 Agent 워크플로다. 상세 설계는
`docs/fullspec/strategy_agent_design.md`를 따른다.

워크플로는 구현과 등록을 맡는 `strategy-author`, 계산과 Evidence를 읽기 전용으로 검증하는
`strategy-verifier`, 사용자 질문과 재배정을 조정하는 메인 세션으로 나눈다.

author는 문서의 빈값, 계산 재료 부재와 실행 능력 부재를 구분한다. 사용자 입력이 필요하면
질문과 확인 사실과 미완료 산출물을 구조화하고 종료한다. 메인 세션이 답을 받은 뒤 이전 상태와
함께 다시 배정한다.

끝점은 전략이 문서대로 백테스트되고 화면에서 상태와 결과를 조회할 수 있으며 verifier의 계산
검증을 통과한 상태다.

## 10. changeset 분리와 순서

작업 순서는 다음과 같다.

1. 계열 정책과 skill 정합을 현재 브랜치에 통합한다.
2. 실행 능력 목록과 드리프트 검사를 구현한다.
3. 런타임 조립의 남은 Web API와 화면 연계, 빈 전략 계열 조합 지원을 완료한다.
4. 등록 절차와 읽기 전용 사전 점검을 완성한다.
5. 공통 전략 계약 검사를 승인된 단위로 구현한다.
6. 계산 검증 방침을 확정한다.
7. author와 verifier 워크플로와 두 인수 시험을 구현한다.

전략 edge 변경은 자금관리와 실행 리팩터링과 분리한다. manual 호환 결과를 먼저 보존하고 Turtle
mode나 기본 정책을 바꾸지 않는다. 전략 구현체의 별도 패키지 이동도 사용자 결정 전에는 이
순서에 넣지 않는다.

## 11. 범위 밖

- 이 단계에서 특정 신규 전략을 채택하지 않는다.
- 이 단계에서 하이킨아시, 멀티 timeframe, 구조 기반 손절, 부분 익절, 트레일링과 거래 간
  리스크 기능을 구현하지 않는다.
- `required_indicators`와 `required_indicators_json`의 역사적 필드 이름을 바꾸지 않는다.
- 운영 중 임의 카탈로그 쓰기 API를 만들지 않는다.
- 사용자 승인 없이 자금관리 기본 정책이나 기존 manual 결과를 바꾸지 않는다.

## 12. 완료 기준

- canonical contract와 skill이 지표와 패턴을 포함하는 계열 정책으로 일관되어야 한다.
- 실행 능력 목록이 조회 가능하고 실제 코드와 어긋나면 검사가 실패해야 한다.
- 신규 Adaptee가 두 실행 서비스에서 적재되고 Web API와 화면에서 실행 가능한 상태로 보여야
  한다.
- 일반 계열이 없는 전략과 Turtle 정책 조합이 실행되어야 한다.
- 등록 절차가 카탈로그와 `StrategyProfile`의 모든 작성 근거를 설명해야 한다.
- 읽기 전용 사전 점검이 코드, 허용 목록과 멱등 SQL의 불일치를 실행 전에 잡아야 한다.
- 공통 계약 검사가 허용 목록 전체에 적용되고 결함 주입으로 검증되어야 한다.
- 계산 검증 방침이 독립 재계산, 판단 대조, Evidence 검산과 수행 시점을 포함해야 한다.
- author와 verifier가 역할을 분리하고 구조화된 사용자 입력 종료 규약을 따라야 한다.
- 두 샘플 문서에 대한 재료 및 능력 판정이 사람이 확인한 결과와 같아야 한다.
- 기존 전략 판단, manual 호환 결과, 기본 정책과 Evidence가 달라지지 않아야 한다.
- 저장소의 pytest, mypy와 ruff가 통과하고 건너뛴 검사 수를 함께 보고해야 한다.

## 13. 열려 있는 결정

전략 구현체를 별도 패키지로 옮길지는 결정되지 않았다. 책임 경계의 이점과 새 패키지 의존 및
검증 비용을 함께 보고 사용자가 선택해야 한다.

공통 전략 계약 검사를 한 changeset에서 완성할지 검증 층별로 나눌지도 결정되지 않았다.

두 인수 시험이 요구하는 하이킨아시와 고급 실행 능력을 Agent보다 먼저 구현할지, Agent를 먼저
만들어 정확한 부재 보고를 인수 시험으로 삼을지도 결정되지 않았다.

## 14. 검토에서 바로잡힌 사실

- `AdapterManager`는 이미 카탈로그와 클래스를 연결하고 신원과 선언된 이력을 검사한다. 현재
  `e1fd478`은 여기에 명시적 허용 목록과 전체 다섯 상태 맞춰 보기를 더했다.
- `AdapterManager`가 대조하는 범위는 클래스 신원, 최소 이력, 지원 timeframe과 계열 선언이다.
  전략 판, 기본 파라미터와 `StrategyProfile` 전부를 대조하지는 않는다.
- backtest-service와 signal-service의 카탈로그 어댑터는 등록 쓰기를 거부한다. 등록은 멱등 SQL
  산출물로 관리하고 런타임은 읽기 전용으로 유지한다.
- Engine은 정책 지표 가운데 strategy timeframe 항목만 일반 계열 목록에 합친다. Turtle의 일봉
  `N`은 별도로 계산한다.
- 현재 Engine은 일반 계열 목록이 비면 `max()`를 계산할 수 없어, 캔들만 쓰는 전략과 Turtle
  정책 조합을 지원하지 못한다.
- Web API는 아직 `VesselReference`로 등록 행을 보강하고 카탈로그가 비면 같은 전략을 코드에서
  다시 만든다. 허용 목록의 다섯 상태는 화면에서 사용되지 않는다.
- `core-lib==0.2.0`을 선언하는 서비스는 네 곳이며, 전략 구현체를 직접 소비하는 곳은 세 곳이다.
- v2 데이터베이스는 legacy 데이터를 이관하지 않는 새 프로비저닝으로 재구성되었다. 기존 등록
  행 migration은 현재 3-1의 선행 위험이 아니다.
