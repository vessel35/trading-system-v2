# 3차 로드맵 — 3-0, 3-1, 3-2

이 문서는 내부 서버 런칭 게이트의 마지막 단계인 3차를 셋으로 나눠 기록한다. 순서는
3-0에서 3-1로, 다시 3-2로 이어진다. 각 단계의 스프린트 목표는 그때마다
`.claude/OBJECTIVE.md`에 옮겨 적고, 이 문서는 세 단계 전체의 합의된 계획을 보관한다.

분할은 2026-07-31 사용자 지시로 확정했다. 원래는 3차 하나였고 내용은 지금의 3-2였다.

## 왜 이 순서인가

전략을 만들려면 지표가 있어야 하고, 전략을 만드는 방법이 정해져야 분석 도구가 무엇을
근거로 개선점을 말할지가 생긴다. 지표 없이 방법을 정하면 예행이 막히고, 방법 없이 분석
도구를 만들면 판정 기준이 빈다.

## 3-0. 지표 추가 개발

**목표.** 전략이 쓸 지표를 실제로 갖춘다.

**현재 상태(2026-07-31 확인).** `core_lib.indicators`의 기본 레지스트리에 등록된 지표는
여섯 종이고 파라미터 조합으로는 아홉 개다.

| 지표 | 등록된 조합 |
|---|---|
| ATR | period 14 |
| Bollinger Bands | period 20, multiplier 2.0 |
| EMA | period 9, 21, 55, 200 |
| RSI | period 14 |
| Stochastic | period 14, smooth_period 3 |
| Volume SMA | period 20 |

외부에 알려진 방법 대부분은 이 목록 밖의 지표를 쓴다. 지표가 없으면 신규 전략 개발은
첫 단계에서 막힌다.

**수식의 표준.** 계산식은 `technical_indicators_calc_spec.md`(개발지침 디렉터리, 917줄)가
소유한다. `docs/fullspec/A1_indicator_inventory.md`가 확정한 대로 legacy signal-service의
지표 코드는 **계산식 이식 원천이 아니며**, 표준 문서대로 새로 구현한다. 표준 문서는 아직
저장소에 미러되지 않았다. `50_metrics_reference.md`를 `docs/fullspec/`로 미러한 선례가
있으므로 같은 방식으로 미러하고, 정본은 개발지침 디렉터리에 둔다.

**지켜야 할 불변식(A1이 확정).** 상태를 가지는 재귀형 지표는 확정된 캔들로만 갱신한다
(`close_time ≤ 판단 시각`, 진행 중 캔들 금지). 계산은 float64로 하고 Decimal 변환은 지표
밖 체결 관문에서 한다. 같은 지표를 두 번 구현하지 않는다. 워밍업 seed와 표준편차 분모
규약은 표준 문서가 통일하며 기존 코드의 규약을 계승하지 않는다.

**검증 방식.** 기존 네 테스트가 모델이다.
`test_indicator_registry.py`(등록·조회), `test_indicator_contracts.py`(계약),
`test_indicator_primitives.py`(원시 계산), `test_indicator_parity.py`(벡터 경로와 O(1)
증분 경로가 같은 값을 내는지). 새 지표도 같은 네 축을 통과해야 한다.

**이 단계에서 정해야 할 것.**
- 표준 문서의 82종을 전량 구현할 것인가, 전략이 요구하는 것부터 우선순위로 구현할 것인가.
  기존 결정([[indicator-count-not-a-contract]])은 "82는 현재 수집분일 뿐이고 계약은 공통
  관리 방식"이므로 개수는 계약이 아니다. 다만 3-1의 Agent가 미구현 지표를 만날 때마다
  멈추므로, 어느 범위까지 미리 갖출지는 정해야 한다.
- 각 지표의 **기본 등록 조합**(파라미터)을 무엇으로 둘 것인가. 조합이 등록되어 있지 않으면
  전략이 선언할 수 없다.

## 3-1. 신규 전략 개발 skill·Agent·테스트 방침

**목표.** 신규 전략을 어떻게 만들고 무엇으로 판정하는지를 정하고, 그것을 실제로 굴릴
Agent를 만든다. 산출물은 문서와 skill과 Agent 정의이며 생산 코드 변경은 원칙적으로 없다.

**출발점.** 코드 계약 층은 이미 있다. `.claude/skills/develop-trading-strategies/SKILL.md`가
`docs/strategy-authoring-contract.md`(444줄)를 표준으로 가리키고, 계약은 책임 경계·파라미터
분리·지표 선언·등록 일치·Evidence·필수 테스트·완료 체크리스트를 규정한다. 이 층이 다루는
것은 코드 정확성이며, 없는 것은 연구 흐름과 판정 방침이다.

**네 갈래.**

- **G-1. 기존 skill을 뼈대로 보완.** 새 skill을 만들지 않는다. 먼저 skill과 계약이 현재
  코드와 어긋난 곳을 찾아 고친다. 자금 관리 정책 런타임 도입, 정책이 가져간 책임(ATR·
  레버리지), 레지스트리 대조 도입 이후의 상태를 코드와 대조한다. 보조 skill이 어느 단계에
  개입하는지 정하고 `.claude/HARNESS.md` 라우팅 표와 맞춘다.
- **G-2. 단계별 산출물과 등록 절차.** 각 단계가 무엇을 남기는지 명시한다. 등록 절차는 특히
  깊게 다룬다 — 필요한 timeframe을 정하는 근거, 각 지표가 값을 내기까지 참조해야 하는 선행
  값의 범위 산정, 그 결과를 `min_history`·`required_indicators_json`·`supported_timeframes`로
  옮겨 `signal_db.strategy_registry`에 등록하는 절차, 지표 조합 선등록의 순서, 코드 선언과
  등록이 어긋나면 `AdapterManager`가 실행을 거부한다는 사실의 사전 확인. 계약 §3.5~§3.7이
  규칙은 정했으나 절차는 비어 있다.
- **G-3. 기반 방침 유지 + 계산 검증 추가.** 판정 수치는 기존 표준(`core_lib/eval/thresholds.py`,
  `docs/fullspec/50_metrics_reference.md`)에서 인용하고, 새로 정하는 값은 그렇다고 명시한다.
  그 위에 신규 전략의 계산 검증을 더한다 — 지표 값의 독립 재계산, 판단의 손 계산 대조,
  Evidence에서 되짚은 손익·비용 검산(`test_trade_money_golden.py`가 모델), 수행 시점, 그리고
  통과하지 못한 전략은 성적과 무관하게 채택하지 않는다는 규칙.
- **G-4. 신규 전략 개발 Agent.** 입력은 외부에 알려진 방법을 사람이 텍스트로 적은 설명이고
  끝점은 등록되어 테스트까지 마친 전략이다. 설명에서 빠진 것을 찾아 **사용자와 대화로**
  확정하고(임의로 메우지 않는다), 쓸 지표를 v2 등록 목록과 대조해 미구현이면 **구현에 필요한
  정보를 사용자에게 요청**하며, skill을 따라 코드를 쓰고, 방침에 따라 테스트 방법을 정의해
  테스트 코드를 쓰고, 등록하고 실행한다. 이 하네스의 subagent는 사용자와 직접 대화할 수
  없으므로 대화를 어디서 수행할지가 설계 결정 사항이다(질문을 구조화해 돌려주고 메인 세션이
  묻는 방식이 유력).

## 3-2. `claude -p` 분석 파이프라인

**목표.** 백테스트 결과를 읽어 전략 개선 지점을 찾는다. 원래의 3차다.

**현재 상태.** 미구현이다. 저장소에 `claude -p`나 관련 호출이 없고 `docs/webui-ux-design.md`가
"콘솔의 존재 이유는 전략 개선 연구"라고 의도만 서술한다.

**재료.** 2차에서 3차로 넘긴 항목들이 여기 속한다. 증거의 빈 껍데기 네 엔티티
(`MISSED_OPPORTUNITY`, `CONDITION_SIGNATURE`, `CONDITIONAL_EXPECTANCY`, `FINDING_CLAIM`)는
스키마에만 있고 엔진이 기록하지 않는다. 사전등록 쓰기 엔드포인트도 없다. 분석이 읽을 재료가
이 기록 경로에서 나오므로 순서상 먼저 채워야 한다.

## 이후 단계

4차 paper와 5차 real은 개발 머신에서 진행하며 런칭 게이트를 막지 않는다. 내부 서버에서는
전략 개발을 하고, 전략 개발과 4·5차가 끝난 뒤 실제 paper에서 real로 넘어간다.
