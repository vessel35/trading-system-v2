# Clean Code Principles

이 skill은 모든 프로젝트에서 클린 코드 원칙을 적용합니다.

## 핵심 원칙

### 1. 의미 있는 이름 (Meaningful Names)
- 변수, 함수, 클래스 이름은 의도를 명확히 드러내야 함
- 약어 사용 최소화, 검색 가능한 이름 사용
- 한 개념에 한 단어 사용 (일관성)

```
# Bad
d = 86400  # elapsed time in seconds

# Good
SECONDS_PER_DAY = 86400
elapsed_time_in_seconds = 86400
```

### 2. 함수 (Functions)
- 함수는 한 가지 일만 수행
- 함수 길이는 20줄 이하 권장
- 인자 개수는 3개 이하 권장 (많으면 객체로 묶기)
- 부수 효과(Side Effect) 최소화
- Command-Query Separation: 명령과 조회 분리

### 3. 주석 (Comments)
- 코드로 의도를 표현하고, 주석은 최소화
- TODO, FIXME 등 표준 주석 태그 사용
- 코드를 설명하는 주석보다 "왜"를 설명하는 주석

### 4. 포맷팅 (Formatting)
- 일관된 들여쓰기와 공백
- 관련 코드는 세로로 가깝게 배치
- 파일당 200-500줄 이하 권장

### 5. 오류 처리 (Error Handling)
- 예외를 사용하여 오류 처리
- null 반환 대신 Optional/Maybe 패턴 또는 예외 사용
- 구체적인 예외 타입 사용

### 6. DRY (Don't Repeat Yourself)
- 중복 코드 제거
- 단, 과도한 추상화 주의 (Rule of Three)
- **Surgical Edit Discipline과 충돌 시**: 사용자 요청 범위 내에서만 DRY 적용. 작업 범위 밖에서 발견한 중복은 별도 이슈로 기록만 하고 같은 PR에 포함하지 마라 (아래 "Surgical Edit Discipline" 섹션 참조)

### 7. KISS (Keep It Simple, Stupid)
- 단순한 해결책 우선
- 불필요한 복잡성 제거

### 8. YAGNI (You Aren't Gonna Need It)
- 현재 필요한 기능만 구현
- 미래를 위한 과도한 설계 지양

## Surgical Edit Discipline (정밀 편집 원칙)

> **출처**: Andrej Karpathy의 LLM 페일모드 관찰 (2026년 트윗) — Karpathy 4원칙 P3 (Surgical Changes)
> 캐노니컬 정의: `genius-thinking` skill의 "부록: LLM 코딩 4원칙" 참조

### 배경

LLM이 코드를 작성할 때 가장 흔한 실수 중 하나는 **작업 범위를 벗어난 변경**입니다. 이해 못 한 코드/주석을 임의로 수정하거나, "기회를 봐서" 리팩토링하거나, 자신의 스타일로 다시 쓰는 행위. 이는 사용자 의도를 흐리고 diff 노이즈를 만들며 회귀를 유발합니다.

### 핵심 규칙

1. **변경된 모든 줄은 사용자 요청에 직접 추적 가능해야 한다**
   - 이 줄을 왜 바꿨는지 한 문장으로 설명할 수 없으면 되돌려라
2. **망가지지 않은 것을 리팩토링하지 마라**
   - 작업 중 마주친 "정리할 만한" 코드는 **`handoff_notes.md`의 TECHDEBT 섹션**에 기록만 하고 손대지 마라
   - 이는 위 "DRY (Rule of Three)" 원칙과 충돌 시 항상 우선
3. **자신만의 스타일로 다시 쓰지 마라**
   - 기존 들여쓰기·명명·import 순서·주석 스타일을 따라라
   - "내 방식이 더 좋다"는 판단으로 일관성을 깨지 마라
4. **주변 코드/주석을 임의로 삭제·수정하지 마라**
   - 의미를 모르는 코드는 보존하고, 필요시 명시적으로 질문

### 자기 검증 질문

코드 변경 후 diff를 검토할 때:
- [ ] 이 변경이 사용자가 명시적으로 요청한 것인가?
- [ ] 이 변경 없이도 사용자 요청이 충족되는가? → 그렇다면 제거
- [ ] diff에 "기회를 봐서 정리한" 변경이 섞여 있는가? → 분리
- [ ] 시니어 엔지니어가 "이 변경은 작업과 무관한데?"라고 할 만한 부분이 있는가?

### 신호 (이 원칙이 작동할 때)

- diff에 불필요한 변경이 적다 (주로 추가, 핵심 함수 1-2개)
- 기존 명명 규칙·들여쓰기·import 순서가 보존된다
- 함수 시그니처가 요청 범위 내에서만 변경된다
- "왜 이 부분이 바뀌었지?" 같은 리뷰 질문이 줄어든다

## 체크리스트

- [ ] 이름이 의도를 명확히 표현하는가?
- [ ] 함수가 한 가지 일만 하는가?
- [ ] 함수 길이가 20줄 이하인가?
- [ ] 함수 인자가 3개 이하인가?
- [ ] 중복 코드가 없는가?
- [ ] 적절한 오류 처리가 되어 있는가?
- [ ] 주석이 "왜"를 설명하는가?
- [ ] 코드가 읽기 쉬운가?
- [ ] **변경된 모든 줄이 사용자 요청에 추적 가능한가? (Surgical Edit)**
- [ ] **작업 범위를 벗어난 변경이 diff에 섞이지 않았는가?**
